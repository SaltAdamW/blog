Requesty：模型路由要同时算缓存损失和故障等待

原文：What is an AI Gateway? The View from Trillions of Production Tokens · 2026-08-29

同一模型可以由多家服务商提供。直觉上，每次选择单价最低的一家就能省钱，但长任务往往反复提交已有对话，上一轮留下的缓存也会影响这一轮成本。Requesty 的运营者用自己的生产流量说明了这种差异。

在其统计中，会话后续请求留在原服务商时，缓存命中率为 91%；换服务商的后续请求为 62%。两组请求的实际费用占标价比例也不同。换路由时，表面上买的是同一模型，实际失去的可能是已经可复用的前缀。只比较价目表，容易漏掉这部分重新读取上下文的成本。

但始终留在原服务商也有另一种失败。作者在一个近期三十天窗口中观察到，3.2% 的请求遇到可重试错误；其中相当多的快速重试仍被发回刚刚失败的服务商。对 38% 的失败，在同一分钟里能找到成功率至少为 95% 的同模型家族替代服务。这个结果提示，重试策略需要看到当前服务状态，而不只是照着固定顺序再试一次。

两种观察放在一起，才有路由设计上的取舍：服务健康时维持会话连续性，可能有利于缓存；服务故障时，又不能为了缓存一直等待。要判断切换是否合算，需要把缓存命中、实际费用、失败等待时间和最终完成情况一起记录。

这些数据来自 Requesty 的付费客户流量，排除了自带密钥流量，且有区域和客户群偏向。它不是随机分流实验，不能把两组差额全部归因于换服务商，也不能当作整个行业的缓存表现。文章值得读的地方是运营者展示了哪些观测量，而不是证明任何团队接入网关都会获得同样收益。

Lemmalog：错误前提被撤回后，依赖它的结论怎么办

原文：I accidentally turned LLM memory into program analysis · 2026-08-28

一次代码调查已经排除了某条思路，Agent 几小时后却又把它提出来。原因可能是旧笔记仍然很容易被检索到，而“这条观察后来被推翻”只存在于另一段对话中。把两段都塞回上下文，还需要模型重新判断哪些结论受到影响。

Jordy Zomer 的 Lemmalog 尝试把这一步交给可维护的推导状态。模型负责从代码、调试器输出和自然语言里提取事实；Datalog 引擎根据事实和规则推导结论，并记录每个结论依赖哪些依据。以后撤回一个前提，就能更新受影响的推导，而不必让模型从全部历史里重新梳理。

删除结论不能简单地沿依赖关系一删到底。假如 A 和 B 各自都能支持 C，撤回 A 后，C 仍有 B 支撑；只有支撑都消失，C 才应被移除。对随时间改变的事实，系统还保留有效区间，区分“现在成立”和“当时为什么这样判断”。这些信息也让人能追问结论究竟从哪里来。

确定性推导没有消除信息入口的错误。作者发现，某些跨会话问题答不出来，是因为事实根本没有被抽取；同一辆车在不同会话中被当成不同实体，也会让关系断开。系统因此保留原始片段，并结合实体归并与语义检索。自然语言中的条件和细微差别，不能都压成无条件事实后就丢掉原文。

在其 LongMemEval 设置中，回答模型每题看到的上下文从约 10.4 万 token 缩到约 2700，但前面还有一次抽取成本，不能写成总费用降低约 38 倍。另一项 LoCoMo 评测中，总体表现也没有超过完整上下文基线。更重要的是，两者都是对话记忆评测，作者最初关心的长时间漏洞调查仍待验证。现阶段可借鉴的是怎样维护依据、撤回和时间状态，而非“符号记忆已经胜出”的结论。

HarnessDev：自动改出的 harness，能换一批任务继续用吗

原文：HarnessDev 论文，arXiv v1 · 2026-09-01

让模型写一个 Agent 循环并不难。难的是判断它写出的上下文管理、工具调用和控制流程，能否在没见过的任务上继续工作。如果反复根据同一批失败案例改代码，反馈集上的进步也可能只是对这批案例的适应。

HarnessDev 把开发 harness 的 creator 和运行任务的 executor 分开。前者交付可执行程序，后者在这套程序里处理任务，评测对象因此从一份答案变成了组织执行的代码。创建实验覆盖六个 creator、四类领域和五个 benchmark，另设迭代实验，检查收到执行反馈后能否改进。

论文观察到，反馈集中的提升不一定延续到留出任务，换一个 executor 后，收益也可能改变。这个结果不能概括为“自动改 harness 没用”，它指出了验收时必须分开的条件：在哪批任务上修改，用什么模型执行，又在哪批独立任务上验证。部署时才付出的执行 token，也不能代表前面开发和试错的总成本。

Harness-of-Harness：多日开发怎样接住上一轮的失败

原文：Harness-of-Harness: Multi-Day Autonomous Software Development with Continual Improvement，arXiv v1 · 2026-09-01

软件项目跨多轮开发后，下一轮如果只读到“上一轮基本完成”的总结，就很难知道还缺什么。Harness-of-Harness 把规划、编码和独立测试组织成循环，每轮留下版本化的软件产物、测试证据和下一轮需要处理的问题；材料按当前阶段逐步提供，不要求每个角色重读全部历史。

独立测试的作用在于让失败进入后续开发。规划者据此调整待办，编码者修改项目，测试者再检查修改是否真正生效。这里持续变化的是被开发的软件项目；实验固定了模型和基础 harness，不能因为标题带有 Harness，就说系统在自行训练模型或重写自身运行框架。

多轮最终表现还包含更多开发投入。论文另有固定开发轮次的对照，但不能把它与三轮累计结果混成同一个等预算结论。读这项工作时，可以先沿着一条失败追踪：证据写在哪里，谁把它变成下一轮任务，修复后怎样确认没有遗失原需求。

工作记忆：存了多少，不等于模型实际读到了多少

原文：Measure Before You Manage: Evaluating Agent Working Memory in Coding Agents，arXiv v1 · 2026-08-31

两套 Agent 都限制在同样的上下文预算内，仍可能看到完全不同的材料。一套保存了很多记忆却没检索到关键片段，另一套把片段送进上下文，却花了更多调用来整理它。只比较存储量或预算上限，看不出差异发生在哪里。

这篇工作先描述 55 条执行轨迹，再把记忆策略的校准、留出验证和检索实验分开。它强调同时记录持久保存的内容、实际送达模型的内容、管理记忆的开销和任务结果。这样才能区分“没留下来”“没找回来”和“找回来了但没有用上”。

其中检索对照只有八个完整的六臂任务块，而且这一部分缺少有效的正式修复得分，不能用来排记忆算法的总体名次。现阶段更适合借鉴它的测量口径：为上下文管理增加观测量，再解释策略之间的差异。

LangChain 的 MCP 更新：等待用户回答，不必一直占着连接

原文：MCP in LangChain: Stateless Protocol, Elicitation, and More! · 2026-09-03

工具执行到一半缺参数或需要确认时，调用链需要暂停，并在收到答案后继续。LangChain 此次把 MCP 支持移入主包，通过 FastMCP 处理连接与协议协商，将新版协议的 elicitation 映射为 LangGraph interrupt，再携带用户答案重试请求。工具列表也可按服务端 TTL 缓存，减少每轮发现工具的请求。

本周发布的是 LangChain 适配，所依据的 MCP 规范版本为 2026-07-28，并非本周首次发布协议。公告中的 Python 接口仍为 beta，TypeScript 支持尚待后续；协议核心无状态，也不表示 Agent 的暂停状态和调用方身份可以不保存。
