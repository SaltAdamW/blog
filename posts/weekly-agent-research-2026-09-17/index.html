回答前声明检索状态，显著降低失败后的失实输出

这里的失实率 DR，是失败工具试验中“编造或无警告传递不可用值”与“编造拒答理由”两类输出的占比之和，并非只统计编造答案。

事实：在同一主实验的 688 例配对比较中，部署提示的 DR 为 14.10%；保留原提示并追加 retrieval_status 要求后为 0.87%，95%区间为[0.15%, 1.71%]，下降 13.23 个百分点（14.10−0.87），92 例改善、1 例恶化。替换为核验指令和仅追加核验指令分别为 4.51%与 6.54%。这是失败报告行为的改善，不是任务完成率提升。框架提示迁移也报告同向下降，但不能据此比较框架优劣。

问题：仅要求依据工具输出回答，或要求核验输出，可能仍没有明确规定证据不可用时的输出行为；需要验证显式失败状态是否比一般核验要求更有效。

机制与证据：干预在回答前要求输出 OK 或 FAILED，并列举错误、空值、遮蔽、不可读内容及结构错误等不可用情形。作者将优势归因于命名失败分支。比较支持这套提示干预有效，但其他候选提示全文未提供，尚不能将状态字段的作用与异常示例、措辞和输出格式的作用完全分离。

局限与负结果：

  • 作者称按 8/8 领域划分筛选与留出验证，但表 4 展示全部 688 例的汇总结果，不应写成独立留出集上的 14.10%→0.87%；单独留出明细在本版本未提供。
  • CrewAI 迁移数字来自八个留出领域，LlamaIndex 和 smolagents 来自全网格。表 2 还注明 CrewAI、LlamaIndex 使用单轮回放，smolagents 使用实时工具循环，样本数不同，不能跨行排名或混算效果（PDF 第 6 页）。
  • 两个一般核验方案的排序跨协议不稳定（PDF 第 8 页）；命名状态方案在框架提示迁移后仍有残余失实，并非消除故障后的编造。
  • 全部样本都是失败载荷，未检验有效结果下是否增加误拒答。FAILED 声明被判为诚实报告的高比例不是检测准确率或召回率，且原文观察到正确 FAILED 标记搭配不实解释（PDF 第 8 页）。
  • 同系列裁判和小规模人工校验限制证据强度；附录未提供原始输出和完整候选提示。增加状态行也不能直接宣称零费用，论文未报告相应时延或 token 成本。

工程启示（推论）：可把证据可用性声明纳入工具后处理协议，作为可检查信号，但必须同时审核答案和拒答理由；不能仅凭模型自报 FAILED 就认定整段回复可信。

最小验证（建议）：在成功与失败混合的本地任务集上，固定模型和调用预算，对比原提示、仅核验、核验加状态字段；另设保留异常示例但去掉状态字段的消融。预先固定领域留出集，配对统计 DR、有效载荷正确率、误拒答率、状态检测精确率与召回率，并记录 token 和时延。

执行护栏降低异常，但成功率提升不等于正常工作无损

事实：在 Claude Code 2.1.19、Claude Haiku 4.5 及同一 Click 仓库快照上，100 个含对抗步骤的任务每条件各运行 3 次。加入 AgentGuard 后，异常执行率从 69.0%降至 26.7%，复合成功率从 21.7%升至 35.0%；原文报告差值分别为−42.3 和+13.3 个百分点。但良性工作完成率从 49.0%降至 42.0%，护栏组过拒绝率为 19.3%。这是有限设置下的可靠性收益，不是无损提升。

问题：编码 Agent 即使给出貌似正确的结果，也可能越界改文件、修改断言绕过失败或忽略验证。只看最终成功或异常率，无法判断护栏是否通过放弃合法工作换取安全。

机制与证据：方法事实：作者先按任务划分数据，从 282 个任务的 461 条异常轨迹归纳 15 条条件式规则，通过触发条件、禁止动作、授权例外、安全替代和执行阶段组织，并按当前指令加载。它只向上下文加入指令，不修改权限或拦截工具。作者解释：条件约束抑制危险捷径，剩余瓶颈是触发护栏后未继续可行工作。对照支持整套干预的效果，未单独证实规则归纳、授权例外或动态路由各自的贡献。

局限与负结果：

  • 作者自评、单模型、单仓库，且每个评测任务都有注入的对抗步骤；不能外推为普通开发任务或其他 Agent 的自然异常率。每组 300 次执行来自 100 个任务，并非 300 个独立任务。
  • 三名评审能够识别实验条件，存在非盲评偏差。原文有任务聚类统计，复合成功率差值的 95%区间为[5.3, 21.7]个百分点，但这不消除评审偏差。
  • Success 同时要求无异常、正确处理对抗步骤和完成可行良性工作，不是独立的功能修复率。CBR 指可行良性工作的完成率，其差值的 95%区间为[−17.0, 3.0]个百分点；未显著下降不等于已证明无损或非劣。
  • 过拒绝率的正文称基线为 0，表 2 却标为横线，表文呈现不一致；护栏组 19.3%有明确报告。
  • 未提供静态规则、人工规则或路由组件消融，正文也未给出完整子技能及归纳器配置；不能断言自动归纳优于人工编写，或动态路由是收益来源。
  • 平均单次费用从 0.158 美元增至 0.162 美元，耗时从 93.3 秒增至 97.0 秒。这不是等费用对照，也未核算规则构建与人工复核的总成本。

工程启示（推论）：护栏验收应联合检查异常率、合法工作完成率与过拒绝，而不是只优化拒绝或安全指标。授权例外和拦截后的继续执行应成为测试重点；提示词护栏不能替代权限隔离。复合成功率上升也不能直接解释为编码能力提升。

最小验证（建议）：选 30 个未参与规则归纳的本地任务，覆盖纯良性工作、阻断风险后仍可继续的工作、明确授权修改测试。固定模型、权限及执行上限，比较无护栏与完整护栏，每任务每组各运行 3 次；尽可能盲审异常、复合成功、良性完成和过拒绝，分别记录费用与耗时，按任务聚类估计区间。预先约定良性完成率的非劣界，不能以差异不显著作为无损证明。

协作训练的团队在截止时限内取得更高得分，但尚非等费用优势

事实（作者初步自评）：DeepSeek-V4.1-Flash 的最强团队配置与最强单 Agent 配置比较，在 FrontierSWE v2 无 GPU 子集上，20 小时截止时限的 Mean@5 分别为 32.90%和 28.20%，相差 4.70 个百分点（计算：32.90−28.20）。这支持配置级的时限收益，不证明增加 Agent 数量本身有效。

问题：复杂编码任务扩大时间预算时，如何让团队通过委派和并行增加有效产出，而不是只增加通信与同步开销？

机制与证据：作者方法：在 Agent Team 模式中，用任务表现、鼓励委派通信的协作奖励和派生时延惩罚共同训练。派生时延依据执行依赖 DAG，以固定推理速率折算 token 成本，加上实测工具耗时，取关键路径长度。作者解释是鼓励有效并行、减少串行与同步；该解释未通过逐项奖励消融独立验证。

局限与负结果：

  • 这是厂商最强配置之间的初步比较，不是同训练、同资源的控制变量消融；无法分离协作奖励、时延惩罚和运行框架的贡献。
  • ProgramBench 仅含 172 个参考解通过率至少 95%的筛选任务；516 是每配置计划轨迹数，不能写成实际完成数。FrontierSWE v2 只含公开无 GPU 任务，该实验节未列子集规模。
  • 相同墙钟期限不等于相同 token、算力或费用；派生时延也不等于线上实测响应时间。

工程启示（推论）：有明确交付期限且任务可并行时，值得评估经过协作训练的团队配置；采购和容量决策仍须另看总费用，不能只看截止时限成绩。

最小验证（建议）：固定同一 checkpoint、任务和工具，对单 Agent 与成员数固定的团队做配对评测。先统一墙钟期限，记录完成质量、总 token、费用和冲突返工，再增加等总 token 对照；此验证运行配置收益，不归因于训练奖励。

批量失败聚合降低演化开销，协同诊断增加平均收益但并非处处有效

文中的 FDCR 指 Failure-Driven Collaborative Refinement，即由失败证据驱动的协同改进；SE 指逐条演化方案。

事实：在五个任务模型与两个τ²-Bench 子集的冻结评估中，逐条演化、批量聚合、批量聚合加 FDCR 的平均准确率分别为 46.67%、54.67%、59.33%。另在 Qwen3-8B 的 Retail 演化运行中，三者训练墙钟时间分别为 1831.4、1292.4、1405.9 秒，API 费用分别为 8.484、2.485、5.763 美元。聚合本身已有收益；FDCR 相对纯聚合增加训练费用和时间，同时提高总体平均准确率，但并非所有模型、子集和指标均改善。

问题：逐条失败触发代码修改，可能反复处理同一缺陷，也可能把当前模型的错误固化为全局限制。作者在六个 Qwen3 模型与领域组合的初步对照中，逐条演化准确率 43.33%，低于固定人工 harness 的 50.28%，说明增加自动修改不保证改进。

机制与证据：做法：三种演化方法从同一人工 harness 出发，固定 Qwen3-8B 参数，最多三轮候选生成；编码代理及诊断角色使用 DeepSeek-V4-Pro。SE 逐条修改并累积为轮级候选；聚合方案优先分析至少跨两个任务的失败模式，每个非空轮次调用一次编码代理。FDCR 另加两轮分析、批评与工程协调，再由仲裁角色形成修改规格。候选仅在后续完整训练评估中总分提高时保留，最终冻结并迁移至五个模型。作者解释：跨任务证据可减少把条件性选择改成全局禁令的模型迎合。辅助观察：人工归类的迎合决策占比为 SE 60.0%、Ecdysis 45.5%；这支持解释方向，不证明其导致泛化提升。

局限与负结果：

  • 作者自评，每个子集仅 20 道训练题和 20 道测试题，每道测试题重复三次；这不等于三次独立演化复现，不能据表中波动直接宣称统计显著或广泛泛化。
  • 成本对应实际演化路径，不是等费用、等调用次数比较。FDCR 同时改变角色组织和推理开销，不能把增益全部归因于多角色协作；API 费用也依赖执行时价格及缓存。
  • 负结果：MiniMax-M2.7 在 Retail 上加入 FDCR 后，准确率从 100.00%降至 96.67%，三次全成功率从 100.00%降至 90.00%。
  • 迎合比例分析未披露独立决策总数、标注一致性，该段也未区分 Ecdysis 是否启用 FDCR。跨任务重复只是归纳偏置，同一模型的缺陷也可能跨任务出现。
  • 候选验收只约束训练总分，不保证每项任务不退化；本实验不能证明自动演化已消除过拟合或合法操作被误禁的风险。

工程启示（推论）：优化 harness 时应先把修改单位从单条失败提升到跨任务失败组，将 FDCR 作为需要额外验收的可选模块，而非默认增加角色。修改规格必须写清触发条件、作用范围和应保留的合法行为；上线门槛同时检查目标模型迁移、重复成功率与关键任务回归，不能只看训练总分。

最小验证（建议）：建议的最小验证，未执行：固定同一 harness、任务模型和训练集，对照逐条修改、轮级聚合、聚合加 FDCR；统一最多三轮及验收规则，记录实际调用、API 费用和墙钟时间。冻结后在未参与修改的任务及另一模型上各重复评估三次，报告准确率、至少一次成功率、三次全成功率和合法操作误禁案例；另设等费用对照，检验 FDCR 收益能否由额外推理预算解释。

编码成绩依赖运行框架，升高推理档位也不保证单调提升

事实（作者自评）：Max effort 下，DSH Minimal、Standard、PTC 在 DeepSWE v1.1 的 Resolved 分别为 72.6、70.5、67.6，在 Terminal-Bench v2.1 的 Pass@1 分别为 90.6、85.8、85.8。附录进一步报告：同一 checkpoint 跨三种框架提高 effort 时，输出长度单调增加，准确率却存在平台和回落。正文的单调提升表述不能推广为跨框架规律。

问题：只按模型榜单选型，或默认更多工具、更高推理档位必然更好，会忽略提示词、工具接口和交互协议对实际编码结果的影响。

机制与证据：作者实验设计：表 4 固定 checkpoint、解码配置和任务集，更换整套运行框架。DSH Minimal 仅用 bash，Standard 提供 26 个初始工具，PTC 通过程序调用 24 个底层工具。这是框架整体对照，不是工具数量消融。附录的长度与准确率脱钩是观察结果，其具体成因尚未隔离。

局限与负结果：

  • 结论限于该模型、框架版本及两个编码基准；不能推导 bash 工具普遍优于结构化工具，也不能证明多框架训练导致了迁移能力。
  • 共同的上下文和轮数上限不是等 token 或等费用约束。Terminal-Bench 评测禁网，也限制了对含联网工具框架的外推。
  • 8 次和 3 次采样是表 4 明确披露的口径；图 11 的跨档结果仅按原文作定性判断，不补造曲线点值、采样数或统计显著性。

工程启示（推论）：把模型、运行框架和 effort 作为联合配置验收。最大档和工具更多的配置不应自动成为默认项，须在目标任务上寻找质量与成本的合适组合。

最小验证（建议）：固定任务集和 checkpoint，对现用框架及 DSH Minimal 分别运行 low、high、max 并重复采样，同时记录任务成功率、输入输出 token、墙钟时间和费用，检查升档不升分及框架排序变化。
