开源 Agent 沙箱的设计如何复用环境，又让任务彼此独立

一次准备，如何成为一百个彼此独立的起点？

下载原稿

我们让一个 Agent 修复程序时，往往会把注意力放在它改了哪些代码、测试是否通过，却很少认真看待修改之前的准备过程。项目要拉下来，依赖要安装，解释器要启动，测试框架要发现测试用例。有时还要启动浏览器、加载一份数据，或者等待一个本地服务完成初始化。这些步骤没有直接生成修复结果，却构成了任务能够发生的前提。

只有一个任务时，等待一次通常还能接受。假如我们希望同一份项目同时产生一百条修复分支，让每个 Agent 尝试不同方案，准备工作就会暴露出一个矛盾：这些任务的起点几乎相同，变化却必须相互独立。如果每条分支都从原始镜像重新准备，安装、启动和加载就可能反复执行；直接让一百个任务使用同一个环境，又会让文件修改、变量和后台进程相互影响。

这不是把启动时间调小一点就能回答的问题。我们真正需要知道的是：一项准备工作做完之后，它的结果在哪里？是几个已经下载的文件，是进程里的对象，还是整个虚拟机正在等待请求的状态？如果这个结果可以保存，下一次运行怎样继承它？如果多个任务继承同一个结果，它们修改之后又怎样分开？

本文围绕这些问题讨论开源 Agent 沙箱的设计。首先处理制品与实例：制品保存可以再用的状态，实例让一项任务独立运行。随后讨论，当环境不再持续活跃时，保存状态是否还需要保留执行资源。最后才进入池、租约、绑定和编排：提前准备多少实例，谁有权使用它，后续请求怎样找到它，以及实际环境变化以后谁来恢复期望状态。

这样的讨论顺序很重要。一个恢复引擎可以减少重复初始化，却不负责完整的多租户平台；一个 Kubernetes 控制器可以管理实例归属，却不因此获得内存快照能力。如果把这些层次都放在同一张产品能力表中，很容易把“没有实现这一层”和“这一层实现得不好”混为一谈，也容易拿某个局部原语代替整个交付过程。

E2B、forkd、CubeSandbox、AgentENV、gvisord、Daytona 和 Kubernetes agent-sandbox 会在文中出现，但它们不是一条从落后到先进的序列。我们把它们当作能够查阅实现的例子，观察它们各自在哪个位置保留工作结果、怎样组织共享、又把哪部分成本交给了其他环节。理解这些选择，比记住谁宣称几十毫秒启动更有用。

资料核对日期为 2026 年 9 月 17 日。Daytona 讨论限定在公开版本 v0.190.0；其公开代码与此后的托管产品不是同一个能力范围。其他项目的取材版本和文件列于文末，便于区分已核实实现与后文的机制分析。文中的算例、程序和时间线用于解释原理，不是对项目进行的性能测试。

阅读主线

第一章回答为什么装好软件还不等于准备好运行环境。第二章在此基础上解释，怎样让多个独立实例继承同一份状态而不立即复制所有内容。第三章再把保存的环境与持续占用的机器资源分开。第四章讨论哪些状态应该延续，哪些应该在任务边界丢弃。第五章把这些机制接到真正的实例交付中，解释为什么恢复能力之外仍需要库存、占用权与持续协调。

如果只记住一个问题，可以一直问：这一步究竟保存了哪项已经完成的工作，下一步又凭什么能够安全地复用它？ 后面的快照、写时复制、增量层和预热池，都可以沿着这个问题理解。

一、软件装好了，为什么还不能立即开始工作？

从一次熟悉的 Python 执行开始

假设任务是读取一份销售数据，筛选某个类别，再计算金额之和。我们准备一个镜像，把 Python、pandas 和输入文件都放进去。表面上看，环境已经完整：没有软件需要下载，也没有文件需要从别处复制。可是启动任务以后，结果仍然不会立即出现。

Python 要先建立解释器进程。导入 pandas 时，解释器需要找到模块，加载代码及相关动态库，执行模块初始化。读取 CSV 又不是简单地获得一个文件路径，而是把文本解析为列、数值和内存对象。真正的筛选与求和，只发生在这些步骤结束之后。镜像保存了这些步骤所需的材料，却不一定保存了它们执行后的结果。

这个区别不只存在于 Python。一个已经安装好的浏览器，还要创建进程、初始化运行环境，才能接收自动化请求；一个已经下载依赖的服务，还要读取配置、建立内部数据结构，才能处理业务。具体的初始化内容因程序而异，但问题相同：文件可用，只能证明程序具备启动条件，不能证明它已经处于可工作的状态。

因此，讨论环境复用时，首先要区分“下次不必再下载”和“下次不必再执行”。缓存依赖包省去了下载，缓存镜像层省去了部分构建，保存已经初始化的内存则可能省去程序启动之后的计算。这几种方法都能减少准备成本，却作用于不同步骤。即使都叫作模板，也不能仅从名称判断它们复用了什么。

E2B 的运行时文档明确把创建沙箱描述为恢复一个预先启动的虚拟机快照。模板包含内存、磁盘和虚拟机状态，运行时从中建立新的执行实例。理解这条路径的重点不是“虚拟机启动很快”，而是其中一些原本属于启动的工作，已经在模板构建时执行过了。S01

从文件集合变成可继续执行的状态

为什么不只保存进程里的几个业务变量？对于自己编写的简单服务，当然可以把数据序列化，再在新进程中读取。这是一种有效选择。但通用沙箱执行的是各式各样的程序，运行时通常不知道哪些变量最重要，也不知道如何重新建立它们之间的关系。

以 Python 对象为例，一个表对象可能引用数组，数组背后还有分配器管理的内存。进程里不只有这个表，还有解释器的栈、已导入模块、线程状态和已经打开的资源。若要求每种应用都提供专门的保存与恢复逻辑，复用就变成了应用改造问题，而不是沙箱提供的通用机制。

虚拟机快照换了一个观察层次。它不必理解某个页面保存的是 DataFrame 还是哈希表，而是保存虚拟机继续执行所需的机器状态及内存，并由相配套的磁盘状态支持恢复。Firecracker 的快照支持文档把这些内容区分为虚拟机状态文件、内存文件以及需要由使用者正确处理的磁盘文件。仅拿到其中一个文件，不构成完整可恢复环境。S03

可以从程序执行位置理解这个要求。CPU 下一条指令要访问某段内存，内存里的对象又指向某个文件内容。如果恢复的是新时刻的内存，却配上旧时刻的磁盘，程序可能继续运行，但它看到的环境不再是原来的那个状态。快照必须维持与捕获范围相符的一致性，不能把任意几个时间点的数据简单拼起来。

这也解释了“保存内存文件”和“实现快照协议”的差别。前者是一项数据操作，后者还要协调何时停止变化、何时捕获机器状态、磁盘对应哪个版本，以及什么时候这组数据可以被宣布为可恢复。各运行时可以采用不同实现，但只要承诺继续原来的运行，状态之间的对应关系就不能省掉。

不过，保存通用机器状态并不总比应用序列化更合适。如果应用只需要保留一个很小的业务结果，恢复整个进程可能带回许多无用内容；如果程序本来就能从数据库重建状态，通用快照是否值得采用，还取决于重建工作与保存、读取工作的对比。这是由需要保留的状态范围决定的，不是越深层的复用就必然越好。

真正被复用的是哪个进程

下面用一段简化程序，把文件准备与进程准备放在一起。它只说明一个常驻服务的内部结构，不是任何厂商的 SDK，也不负责调用快照接口。

import pandas as pd

table = pd.read_csv("/data/input.csv")

def handle_task(category):
    selected = table[table["category"] == category]
    return selected["amount"].sum()

如果运行时在模块加载、CSV 解析以及服务就绪之后保存整个环境，恢复出的进程就有机会从已经存在的 table 继续工作。任务参数到来后，可以直接进入 handle_task。这里省掉的是产生 table 的那段过程，而不是仅仅省掉 CSV 文件的下载。

现在稍微改变执行方式：构建模板时运行这段准备脚本，但脚本随即退出。等任务真正到来，再启动一个新的 Python 程序。即使快照能力本身完全正常，也不能据此期待新进程里自动出现同一个 table。已经结束的业务进程不会因为系统曾经执行过它，就把它的业务变量永久登记到所有后续解释器中。

再考虑另一种更容易混淆的情况：准备进程还在，但任务入口调用的是启动子进程的命令接口。新命令会按照自己的执行方式初始化环境，并不等于进入了原来的 Python 会话。沙箱恢复了原进程，只能说明它仍然存在；客户端是否使用它，是另外一段调用关系。

所以，设计预热模板时要同时看两个位置。一个是快照捕获点：想复用的准备结果是否已经产生，承载结果的进程是否仍然存活。另一个是恢复后的执行入口：请求是否确实交给那个进程，还是无意间重新开始了初始化。只核对第一项，会得到“模板里明明预热过，任务却又导入一次”的困惑。S01S10

对命令执行型任务，这并不一定构成错误。如果每个任务本来就是运行一个独立程序，那么重复创建应用进程可能正是所需隔离的一部分。此时镜像缓存、文件页缓存和已经启动的虚拟机仍然有价值，只是不能把收益说成复用了业务解释器的全部内存状态。

对常驻解释器型任务，则要把执行入口当作环境设计的一部分。比如统一通过服务处理请求，或者通过保留上下文的代码执行通道访问解释器。这里无需展开具体协议，只需记住：快照保存的是某个确定的运行，复用也必须落到那个确定的运行上。

就绪探针决定快照保存到哪里

假设我们已经决定保留常驻进程，下一件事就是确定什么时候可以拍快照。过早保存会留下尚未完成的初始化，过晚保存可能把本不属于公共基线的任务状态也带进去。模板构建不能只等待一个固定时长，因为相同程序在不同机器和缓存条件下，准备时间可能不同。

一个直接办法是让应用提供就绪条件。CubeSandbox 的模板构建会启动临时虚拟机，并等待配置的 HTTP 探针返回成功状态，再保存相应环境。这让构建流程能够把“程序自己判断准备完成”作为捕获前提，而不是根据猜测的等待时间行动。S05

但探针不是自动生成的业务正确性证明。检查某个端口可以建立连接，证明的是监听已经存在；检查管理服务能响应，证明的是管理通道可用。假如业务服务还在后台加载数据，那么这些条件都不能说明准备阶段已经结束。探针的意义取决于它具体检查了什么。

仍以数据服务为例，假设服务先启动 HTTP 监听，再异步解析输入。若 /ready 在监听建立时立即返回成功，模板可能保存到表尚未加载完成的时刻。恢复以后，所有实例还要继续解析。这个系统并没有违背“从快照恢复”的机制，只是捕获点没有覆盖我们希望提前完成的工作。

如果把 /ready 定义为输入版本已核对、解析完成、处理请求所需的数据结构已建立，构建流程才能把这段准备纳入公共基线。这里的变化不是换了更复杂的探针，而是让探针的语义与希望复用的结果一致。每多检查一项条件，都应当能说明它消除了恢复后的哪一段必需工作。

另一方面，不能为了使探针看起来充分，就把所有未来可能发生的工作都预先执行。若系统面对很多不同类别的请求，预先读取全部数据、打开全部工具或构建全部索引，可能保存大量绝大多数任务都不会使用的状态。探针应保证公共准备已经完成，不是要求未来任务的全部工作提前完成。

这形成了一个具体的设计取舍：准备得更深，能够减少某些请求恢复后的工作；准备得更宽，则可能扩大快照、增加保存和分发成本。决定点应来自任务的共同部分，而不是来自“模板必须尽可能暖”这样的笼统目标。

公共基线应该在什么地方结束

公共基线不是越接近最终任务越好。设想两个任务使用同一套数据处理代码，但输入文件不同。如果把某个任务的私有输入加载进模板，那么模板已经不再适合任意同类任务；若继续无差别交付，还会造成错误的数据继承。

可以按变化来源划分准备过程。解释器版本、依赖组合、公共代码和经允许共享的数据，适合作为基线候选。任务参数、私有凭据以及只属于某次执行的输入，则通常需要在实例已经独立分配后再提供。这里不是给所有系统规定固定字段，而是在建立判断方法：某项状态能否被下一个任务合法且正确地继承？

用教学场景说明，假如所有任务都分析同一份公开数据，只是筛选条件不同，那么预先解析数据有明确的复用机会。若每个任务分析不同客户上传的表，公共模板可能只能准备好解释器和解析库，真正读取数据仍要发生在领取之后。后一种模板较浅，却更符合它的共享条件。

还有一些配置看似很小，却会改变初始化结果。程序可能根据环境变量选择不同模型，根据工作目录加载不同配置，或根据启动用户访问不同文件。若这些设置已经参与初始化，领取后再改字符串未必能改变内存中已经建立的状态。能否晚些绑定，取决于程序何时读取并固化这个值。

这就是后文预热池需要匹配配置的原因之一。匹配条件不是单纯的产品限制，有时是公共状态能够被复用的前提。如果两个请求对准备结果的期待不同，把它们放进同一个库存桶并不能消除差异，只会把问题推迟到执行时暴露。

从制品角度看，模板最好能够说明自己是哪一组准备条件的结果。依赖、应用代码和捕获时使用的配置共同决定了它的含义。原始镜像相同，并不意味着由它初始化出来的所有内存状态相同；两个模板名称相同，也不能替代对实际版本的管理。这些是从复用条件得到的工程要求，不是某个 API 名称自带的保证。

OCI 镜像为什么只是模板构建的输入

我们平时用镜像标签指代环境，容易把镜像和模板当作同一个对象。对于保存运行态的系统，二者之间还有一次真正的执行。镜像描述可用文件与启动配置，模板构建则要把这些材料变成已经运行过的环境，再保存执行结果。CubeSandbox 的模板文档明确区分了这两类制品：OCI 镜像是输入，根文件系统、微虚拟机快照和运行配置共同形成可以恢复的模板。S05

用一个构建过程来理解。首先取出镜像中的文件，为虚拟机准备能够使用的根文件系统；随后启动虚拟机，让入口程序按照配置运行；应用通过就绪条件表明公共准备已经结束；最后捕获相应状态，并记录以后恢复时需要的配置。前两个阶段没有完成，谈不上一个真实运行点；后两个阶段没有完成，就没有一个定义明确的可复用运行点。

因此，同一个镜像可以产生不同模板。启动命令不同，进程集合可能不同；初始化配置不同，内存中的数据结构可能不同；给虚拟机暴露的资源条件不同，程序启动时作出的决定也可能不同。它们具有相同文件来源，却未必具有相同运行状态。恢复模板时只知道原始镜像名称，可能不足以说明自己继承了哪个起点。

E2B 的构建流程进一步把基础准备、用户步骤、最终准备和优化组织为可缓存阶段。阶段缓存能够避免相同准备反复执行，而最后的快照又保存可恢复的运行结果。这里出现了两种不同复用：构建时复用已经完成的步骤，运行时复用构建好的状态。它们发生在不同时间，不能用“有一个镜像缓存”概括全部作用。S01

这个区分还能解释更新问题。假如只修改了某个任务参数，可能不需要重建公共模板；假如修改的是初始化时加载的应用代码，旧快照里的进程不会因为镜像仓库出现新标签就自动换成新版本。要继承新代码形成的运行状态，需要重新产生相应模板，或者有明确的应用更新协议。

模板作为制品，应当使这个来源关系可以追溯。这里不要求使用某种固定清单格式，但需要能够把实际准备结果与输入版本对应起来。否则同一名称在不同时刻指向不同内容，调用者很难确认一次实验与另一次实验是否真正从相同环境出发。可复用不仅意味着能够读取，也意味着所复用的对象有确定含义。

暂停执行以后，磁盘写入是否已经结束

再看快照捕获中的一个具体细节。程序的一次写文件调用，会经过进程、guest 内核、虚拟设备以及宿主机存储路径。让 guest CPU 不再执行新指令，并不意味着此前提交到其他环节的所有工作都在同一瞬间结束。若仍有在途 I/O，捕获协议必须考虑它们与机器状态的对应。

Firecracker 对暂停状态的说明就保留了这个区别：vCPU 与设备模拟停止之后，已经提交的异步块 I/O 仍可能由内核完成，快照创建会处理相应排空过程；外部设备后端的变化也需要按其支持范围理解。这说明“暂停”是有具体边界的运行状态，不是对所有关联系统发出一个抽象的全局冻结命令。S03

从应用视角看，某些最新数据还可能位于 guest 内存中的文件缓存。若完整恢复包括这段内存及与之相配套的设备状态，它与只保留磁盘并重新启动程序，是不同的恢复语义。后者面对的是磁盘上已经形成的状态，不能假定所有尚在内存中的变化也会凭空出现。恢复范围改变以后，需要重新理解应用能够看到哪些写入。

因此，保存磁盘文件、保存内存和保存机器状态，应被看作一个有关联的协议，而不是任意顺序的文件复制命令。假设在进程仍持续更新时先复制磁盘，再过一段时间复制内存，中间发生的变化可能让二者不再对应。问题不是两个文件各自不完整，而是组合起来并不代表被承诺的那个运行点。

把这个条件讲清以后，就能理解为什么一些实现专门管理只读基线、可写差异和提交时刻。它们需要给每次恢复指定一个确定的数据视图，并让捕获完成后的新变化进入别处。分层存储与写时复制不只是节省空间的技巧，也是在帮助系统组织“哪些内容属于这个版本”。

本文不把一次快照提升为跨所有外部服务的事务。它只要求在声明捕获的本地范围内，数据与机器状态遵守恢复协议。数据库、网络对端或外部卷若不在相同协议里，仍然拥有自己的完成条件。明确范围，才能判断快照已经保证了什么，以及应用还要承担什么。

恢复为何不必先读取全部内存

假设快照保存了大量数据，但刚恢复时程序只需要少量页面来继续等待请求。如果恢复必须先把整个内存镜像读入，再允许任何指令执行，就会把暂时用不到的数据也放到前置等待中。保存得越多，这种等待越明显。

E2B 的运行时采用按需内存加载。Firecracker 恢复虚拟机时，不必先为所有页面提供实际内容；当运行访问到缺失页面时，userfaultfd 将相应事件交给处理器，处理器从模板的内存文件提供所需数据。运行时还可以结合预取，提前读取预计会访问的页面。S01S04

这里需要区分三个概念。地址空间说明程序可以访问哪些位置；保存的内存镜像说明这些位置在捕获时是什么内容；物理内存中已经驻留的页面则说明现在有哪些内容可以直接使用。恢复地址关系，不等于把所有字节都立即读入。正是这种分离，让按需恢复成为可能。

跟踪一次访问就容易理解。程序恢复后准备读取某个变量，所需页面还没有装入，访问于是等待页面被补齐。处理器找到快照中的相应范围，获得内容并使页面可访问，原来的指令再继续。对程序来说，它仍在读取自己的内存；恢复系统承担了把保存的数据接回这次访问的工作。

这种做法减少的是“执行前必须读取的集合”。它并没有让所有页面都不用读取。如果任务稍后访问到另一部分内存，仍然需要获取对应内容。若一个计算从开始就要扫描几乎整个快照，那么按需加载只是把读取分散到访问过程中，不应据此承诺总读取量大幅下降。

反过来，如果任务只接触快照的一小部分，就有机会不读取其余部分。对同一个模板，不同任务的访问模式可能差别很大。因此，快照文件有多大，只说明潜在状态范围，不能直接等同于一次任务必须读取的数据量。程序真正访问的页面集合才决定这部分工作。

磁盘缓存还会改变一次缺页的成本。内容已经在本机缓存时，获取路径较短；需要从较远的存储获得时，等待会增加。所谓“同一个快照恢复”，可能对应不同的数据位置。解释机制时要保留这个条件，否则很容易把一次热缓存下的恢复行为误认为所有恢复的共同结果。

预取是在做预测，不是在消除读取

完全按需读取有一个代价：程序访问缺失页面时必须等待。若运行时提前知道恢复初期经常访问哪些页面，就可以先把它们读进来，减少实际访问触发的停顿。E2B 的模板优化阶段会记录一次新恢复所触及的页面，用作后续预取提示。S01

为什么不直接预取全部内存？因为那会重新接近完整预加载。如果许多页面最终没有使用，提前读取只增加了 I/O 和内存占用。预取本质上是在做有范围的预测：用额外的提前工作，换取较少的临时等待；预测不准确时，就会读取用不上的内容。

例如，一种模板恢复后总是先启动同一个服务，访问固定的代码和数据结构，这部分页面比较适合预取。而任务参数决定的后续数据访问则可能差异很大。把服务恢复所需页面和业务数据页面分开理解，才能解释为什么某些预取在多个任务之间稳定复用，另一些则只能针对特定任务优化。

预取也会与并发产生关系。少量实例恢复时，提前读取可能让它们更快进入可用状态；大量实例同时恢复时，同一存储和缓存路径可能承担集中读取。不能只看单次请求减少了几次缺页，还要看被提前的工作是否集中竞争同一资源。这个结论来自访问路径本身，并不意味着应当一律关闭或开启预取。

在设计上，按需加载与预取不是二选一。可以让必需的公共页面先到位，让其余页面继续按需获得。关键问题始终是：哪部分数据在什么条件下大概率会用到，为它支付提前读取成本是否有依据。将这个问题明确化，比只说“懒加载更快”或“全部预热更快”更接近真实系统。

按需恢复以后，数据来源还需要存在多久

如果恢复之前已经把全部数据复制进独立内存，后续计算对原始快照的读取依赖可能较少。按需恢复则不同：某些页面现在尚未被访问，但未来仍可能需要从保存的数据中取得。因此，恢复接口已经返回，不能成为立即回收底层状态数据的理由。

Firecracker 的文件映射恢复文档明确指出，内存后端需要在恢复后的虚拟机生命周期中保持可用。这里关注的是数据和相应引用的可用性，而不是要求应用程序记住某个任意文件名。共享快照既被未运行状态引用，也可能被正在执行但尚未读取全部页面的实例引用。S03

对用户态缺页处理路径，还需要维持供页逻辑。Firecracker 文档说明，如果负责处理缺页的服务退出，等待页面的运行可能无法继续。因此，懒加载引入的是一段持续的数据依赖，不能把负责读取的组件当作只在创建瞬间用一次的工具。S04

这段依赖让“启动完成”具有更准确的含义：运行已经具备继续执行的条件，并不表示此后完全不再需要快照和读取后端。节点管理、快照删除以及缓存回收，都需要尊重仍在使用的数据关系。它们不一定由同一组件实现，但不能在生命周期上相互矛盾。

反过来，如果任务已经结束、相关映射与读取引用都已释放，仍被保留的数据就只应由其他明确用途继续引用。把可恢复版本、运行依赖和普通缓存分别管理，既能避免过早删除，也能避免因为曾经启动过一个实例就永久保留全部数据。第三章将进一步讨论这种状态保存与缓存的区别。

捕获的世界与外部世界并不完全重合

进程恢复以后，它的内存可以回到捕获时刻，但外部服务并不会一起回到那个时刻。这是通用运行态复用必须面对的边界。一个连接在本地留下了状态，并不表示远端仍然保留相配套的会话；一个内存中的时间判断被恢复，也不表示外部时间停止过。

Firecracker 的克隆网络文档专门讨论快照恢复与克隆时的网络处理，随机数文档也解释了克隆状态后重新建立适当随机性的必要性。它们说明，独立执行不仅是复制内存内容，还涉及恢复后如何与各自的外部环境重新对应。本文不把这些问题展开成网络实现教程，但不能把“保存了内存”写成“所有外部关系都可以原样延续”。S07S08

对公共模板而言，一个容易理解的设计是尽量在接收具体任务之前捕获。这样，模板包含公共程序及初始化结果，却较少依赖某次任务已经建立的外部交互。恢复以后，再为独立实例提供任务输入、身份和需要的连接。具体项目仍需按照自身协议处理，不存在一种快照操作可以自动替所有外部系统安排一致恢复。

对于长会话快照，情况不同：任务确实已经发生过外部交互，保存现场是为了稍后继续。此时上层应用需要理解哪些连接可以重建，哪些操作可能已经成功，以及恢复之后应该从哪一步继续。运行时能够恢复本地进程，不等于它知道业务请求在远端是否完成。

这不是快照机制的偶然缺陷，而是捕获边界决定的结果。只要某项状态不在快照范围内，就不能用恢复本地快照来控制它。第四章讨论任务重建时还会回到这个边界，因为“回到初始状态”同样不能撤销外部世界已经接受的修改。

有状态制品为什么会带来兼容性条件

普通源代码可以在兼容解释器上重新运行，因为解释器会从头建立当前机器所需状态。运行态快照保存的则是已经建立的机器和程序状态。它让恢复跳过了一些重建，也因此要求目标运行环境能理解这些保存内容。这是复用更深状态带来的交换条件。

Firecracker 的快照格式具有独立的版本，恢复时会检查格式兼容性；其版本文档还讨论宿主内核、设备模型与 CPU 特征对恢复的影响。一个快照文件能够被复制到另一台机器，只说明数据运输成功，不说明那台机器满足恢复所需的执行条件。S06

可以想象程序在初始化时根据 CPU 能力选择了某段执行路径。快照把选择之后的状态保存下来，目标机器若不能支持相关执行条件，就不能简单把这份状态当作跨任意硬件通用的文件集合。对设备状态也是同样道理：保存了某种虚拟设备的内部状态，恢复端需要按兼容含义重新建立它。

这并不是说运行态制品完全不能迁移，而是迁移范围需要被明确规定。统一的运行时版本、受支持的硬件条件和设备配置，可以提供一组可管理的恢复目标。若必须面对更异构的环境，则可能需要重新构建模板，或者采用较浅层的文件与应用状态恢复。

这让“复用深度”有了更完整的含义。越多依赖已经执行过的状态，越可能减少重复初始化；同时，恢复对当时执行条件的依赖也需要被管理。仅复用文件的办法要重新计算更多，却可能更容易在不同运行条件下重新建立适配状态。两者的差异是工作发生的位置和前提，不是一个单向递增的先进程度。

准备成本应当沿着一次任务来理解

现在可以把一次任务的准备拆得更准确。某些工作发生在制品构建时，比如安装依赖与完成公共初始化；某些工作发生在实例创建时，比如建立执行环境并恢复状态；某些数据读取被推迟到程序访问时；任务自身的计算则从这些前提之上继续发生。

假设两条路径都返回“沙箱已启动”。路径甲在返回之前读入全部内存，路径乙只恢复必要状态，其他页面等待按需加载。只比较返回时间，可能认为乙省掉了全部读取；只比较第一次业务计算，又可能发现乙在计算中经历更多缺页。两者都没有违反自身机制，差别在于观察点覆盖了哪些工作。

因此，若要检验模板设计是否真正减少重复准备，应当从同一项业务操作追踪它需要的阶段。安装是否仍重复，解释器是否仍新建，输入是否仍解析，恢复后的第一次处理又读取了哪些内容。先建立这些因果，再选择测量位置，才有办法把变化归到具体机制，而不是把所有差异都归给“冷启动”。

这不要求每篇原理文章都附一组性能数据。没有统一负载和真实测试时，我们仍能准确说明某项机制避免了重复计算、延后了读取，或改变了必须驻留的数据范围。不能越过的界限是，把工作量变化直接写成所有任务、所有机器上的延迟保证。

第一章到这里完成了一个重要转换：准备好的环境，不一定只是可执行文件的集合，也可以是一段已经执行到明确位置的运行状态。但保存并恢复一次，还没有回答一百个任务怎样同时继承它。下一章要处理的，正是完整复制与共同修改之间的那条分界。

二、一份准备好的环境，怎样变成一百份独立环境？

相同的起点，不等于相同的后续运行

现在我们已经有一份可恢复的环境：程序完成了初始化，公共数据已经装入，虚拟机停在一个明确的准备点。第一个任务从这里恢复，避免了重复准备。第二个、第三个任务也希望从同一位置开始，问题就从“怎样继续”变成了“怎样分别继续”。

最直观的办法是为每个任务复制完整磁盘和内存。这样每个实例都有自己的字节，修改不会影响其他实例。从正确性直觉上看很容易理解，但代价也很明确：任务还没有做任何不同的事情，系统就先为它们复制了大量相同内容。若公共状态很大，这项工作可能比后续真正的任务修改还多。

另一种直觉是让所有任务直接访问同一份内存。这样不用复制，却改变了任务语义。一个任务更新变量，另一个任务可能看到；一个任务重新初始化某个对象，其他任务的计算就可能受到影响。对于并行搜索、独立测试或互不信任的执行，这通常不是我们希望得到的环境。

真正需要的，是把逻辑独立与物理重复分开。每个任务应当拥有独立的状态视图，但这些视图在内容相同时，可以暂时引用同一份底层数据。只有出现分歧的部分，才必须获得自己的存储。写时复制正是围绕这个条件工作：先共享相同内容，修改时再建立私有版本。

这不是把隔离要求降低了一点。任务看到的仍然应该是自己的内存与文件。变化的是系统什么时候支付复制成本，以及是否有必要为从未发生分歧的内容支付这项成本。只要共享的边界和写入分离正确，逻辑上的独立不要求一开始就存在完整的物理副本。

forkd 的基础路径保存了什么

forkd 的基础机制从一个预热后的虚拟机快照开始。父环境完成准备并保存后，各个子实例作为独立的 Firecracker 进程运行，通过 MAP_PRIVATE 映射保存的内存镜像。运行时借助宿主机的内存映射与写时复制机制，使尚未变化的内容能够共享，写入后的页面则成为实例自己的内容。S10

这里要先澄清“父”和“子”的含义。它们表达状态来源关系：子实例从父环境某一时刻的快照继承起点。不能据此想象所有 Agent 都在同一个正在运行的 Python 进程里，也不能推断一个父虚拟机必须一直执行，才能维持子实例读取。基线是保存的状态，子实例各自有运行它的虚拟机进程。

这一点与直接共享服务很不一样。若一百个客户端连接一个公共 Python 服务，服务的内存对象就是共同运行状态；而从同一快照恢复出一百个虚拟机，程序虽然从相同起点继续，后续运行却分属不同实例。底层页面可以相同，并不意味着上层进程身份、指令执行和写入结果混在一起。

为什么文档会用接近 fork 的方式描述？因为从效果上看，新实例继承了一份已经初始化的地址空间，并让后续写入私有化。可是系统实现仍要建立虚拟机、处理设备和网络、管理进程及资源。不能把这个名称理解成调用一次普通进程 fork() 就自动获得整个沙箱平台。

反过来，也不要因为底层仍有虚拟机创建工作，就认为状态继承没有价值。真正被移除的是重新生成公共状态的那一段，以及可能避免的整份数据复制。衡量机制时，应当分别看它消除了哪些工作、仍保留哪些工作，而不是在“等同于进程 fork”与“完全是冷启动”之间二选一。

一个地址为什么可以对应不同的结果

理解内存共享时，容易被“相同地址”误导。程序使用的是自己的地址空间。两个实例都访问某个位置，并不表示它们在操作一个共同业务变量；这些地址如何映射到底层页面，由各自的执行环境和宿主机内存管理共同决定。

在共享基线阶段，实例 A 的某个页面位置与实例 B 的相应位置，可以由同一份只读底层内容支持。它们读取到的值相同，因为快照中的初始值相同。系统无需为这种相同的读取行为预先保存两套字节。

当 A 对页面写入时，情况改变了。系统需要给 A 一份能够独立修改的页面，并让 A 的映射指向它。B 的映射仍保留原来的内容。此后 A 再次读这个位置，得到自己的修改结果；B 读取对应位置，得到公共基线值。这个分离过程正是任务状态开始分歧的位置。

MAP_PRIVATE 的接口语义也强调这一点：映射中的更新不对其他映射同一文件的进程可见，也不会写回底层文件。它提供的是私有写入视图，而不是让所有使用者共同更新同一块共享内存。S09

不过，私有映射不能替代对基线本身的管理。Linux 手册并不承诺，在映射建立之后随意修改底层文件，会以某种适合作为模板更新的方式传播到所有现有映射。公共快照应被当作确定版本使用，不能一边让任务继承，一边原地改变它的含义。需要新的准备结果时，生成新版本比修改正在被共享的基线更符合这种模型。S09

这也说明了不可变制品的重要性。不可变不只是方便缓存：它让一个快照引用在不同实例之间始终指向相同的起点。没有这个前提，任务 A 和 B 即使声称使用同一个模板，实际看到的初始内容也可能取决于开始时间，独立比较就失去了可靠基础。

用两个私有映射观察分歧

下面的程序在 Linux 上用两个私有映射读取同一个临时文件，再只修改其中一个。它演示的是写入可见性，不是虚拟机克隆，也不能用来测量某个项目的物理内存节省。

import mmap
import tempfile

with tempfile.TemporaryFile() as backing:
    backing.write(b"A" * mmap.PAGESIZE)
    backing.flush()
    with mmap.mmap(backing.fileno(), 0, access=mmap.ACCESS_COPY) as left:
        with mmap.mmap(backing.fileno(), 0, access=mmap.ACCESS_COPY) as right:
            left[0:1] = b"B"
            backing.seek(0)
            print(left[0:1], right[0:1], backing.read(1))

输出应为 b'B' b'A' b'A'。左侧视图看到自己的写入，右侧视图仍看到原内容，文件本身也没有被改成 B。将文件视为基线，将两个映射视为两个独立视图，就能看到共享与分歧之间的关系。需要注意，真正的沙箱还包含远多于这个程序展示的状态和隔离机制。S09

这个例子还可以帮助理解为什么写入统计很重要。假如任务只读取，私有写入就没有发生；假如任务把映射全部重写，原本能够共享的区域会逐步转成私有。创建完成的那一刻看起来很省，并不能代表任务执行一段时间后仍然保持同样的共享比例。

页面粒度也会改变直觉。我们在业务代码里修改一个字段，内存管理看到的却是包含这个字段的页面。它并不知道该字段只代表一个很小的业务变化。只要写入触发了页面私有化，就可能为整个页面支付分离成本。这是系统粒度与业务粒度之间的区别，不能用变量数量来直接估算私有内存。

因此，讨论“克隆很多实例只增加很少内存”时，至少需要知道这些实例做了什么。仍然等待请求的实例、只读公共数据的实例，以及不断构建新对象并更新状态的实例，可能呈现不同的内存增长。机制提供的是共享机会，而不是对任意运行轨迹的固定占用保证。

磁盘上的独立文件可以共享区段

再看文件系统。假如每个任务都获得自己的项目目录，最简单的实现是逐字节复制；但对于装满相同依赖的根文件系统镜像，这仍然会重复写出大量相同内容。文件系统的 reflink 提供了类似思路：创建独立文件，让底层存储区段在内容未变化时继续共享。

CubeSandbox 的 CubeCoW 使用 XFS reflink，通过 FICLONE 管理根文件系统和内存快照卷。克隆后的文件可以有自己的身份和后续修改，但初始数据区段不需要全部重写。Linux 对 FICLONE 的说明也将其描述为共享底层存储，并通过写时复制维持后续修改的分离。S11S12

从文件名看，两个镜像已经不同；从逻辑内容看，它们最初完全一致；从物理存储看，一些区段仍由双方共同引用。这三个层次并不冲突。对任务来说，重要的是它写入自己的根文件系统后不会改掉别人的文件；对存储系统来说，则是在满足这种语义的前提下避免立即复制相同内容。

假设两个任务都从同一项目开始，A 修改一个源文件，B 只运行测试。支持相应 CoW 的存储路径可以让 A 的变更进入私有区段，而其余未修改内容继续引用基线。这样，空间增长更接近实际发生的分歧，而不是“实例数乘以整个项目体积”。这只是机制推导，具体增长仍由文件系统、写入方式和其他数据决定。

尤其要注意，某些业务操作看起来只改了很少文本，底层程序却可能重写整个文件。编辑器的保存方式、数据库的写入模式和构建工具产生的中间文件，都可能改变实际写入范围。共享机制按它看到的存储修改行动，并不自动理解业务上的差异有多小。

这种路径也有适用条件。文件系统必须支持相关克隆语义，克隆不能任意跨越不支持共享区段的边界。把数据搬到另一台机器或另一类存储，并不会因为文件源自 reflink 就免除传输。本文讨论的 CubeCoW 路径是在其所要求的文件系统条件下成立，不是所有文件系统都具有相同行为。S12

内存文件的克隆，不等于运行内存已经共享

内存快照也保存在文件中，于是很容易产生一种推断：既然这个文件可以 reflink 克隆，多个恢复后的虚拟机就一定只占一份物理内存。这个推断跨越了两个不同机制。

reflink 首先决定文件数据在存储层如何共享。虚拟机恢复之后，内存通过什么方式映射、是否使用同一底层对象、页面是否进入同一页缓存路径，以及写入如何形成私有页面，都属于运行时读取和内存管理。两个逻辑文件共享磁盘区段，不足以独立证明其驻留内存也完全共享。S09S11S12

对 forkd 的基础路径，我们关注的是多个实例对保存的内存镜像建立私有映射，未变化页面能够通过相应内存路径共享。对 CubeCoW，我们关注的是文件克隆避免了对底层存储区段的即时复制。两者可以出现在同一系统中，也可以由不同实现分别承担，但不能因为都叫 CoW 就把效果相加而不检查路径。

这也是为什么“零复制”必须限定范围。若指某次文件克隆不逐字节复制已有区段，它并不自动涵盖捕获前冻结、变化内存落盘、虚拟机恢复或新设备创建。如果某些阶段需要写出修改后的内容，相关 I/O 仍然存在。局部没有整份复制，不等于端到端没有任何数据搬运。

CubeSandbox 的架构文档还描述了增量保存变化内存的做法。它与 reflink 的关系可以这样理解：没有变化的存储部分继续共享，需要保存的新内容则写入对应的新版本。这解释了为什么快照可以减少写放大，也解释了为什么写入密集的工作负载仍会产生实在的持久化成本。S11

比较两个设计时，最有效的问题往往不是“谁支持 CoW”，而是沿着一份数据问：它在磁盘上是几个逻辑文件，实际占了多少区段；恢复后由哪个对象映射；读取时在哪个缓存中复用；第一次写入后生成的是私有内存，还是新的存储区段。答案越具体，越不容易把不同层的节省混成一个数字。

快照、克隆与回滚分别改变什么

这些系统常同时提供快照、克隆和回滚，但三个词改变的对象不同。以 CubeSandbox 的公开接口说明为例，快照保存当前状态以便以后使用；克隆从某个当前状态派生新实例；回滚则让原实例回到之前保存的状态。它们可能共享底层保存与恢复机制，却不应拥有完全相同的业务含义。S30

可以用一个教学场景区分。Agent 在项目上完成了依赖安装，还没有修改代码，这时保存快照 S。之后希望尝试三种修复，便从 S 创建三个独立分支。每个分支都有自己的变化，S 保持为共同起点。如果某一分支发现方向错误，可以在它自己的生命周期内选择回到 S，再尝试另一条路线。

在这个过程中，状态来源和实例身份是两条线。三个分支来自同一个 S，并不意味着它们属于同一个当前实例；一个实例回到 S，也不等于新的分支自动获得了它原来的业务身份。接口是否保留沙箱标识，是具体产品语义，不能从“恢复了同一份字节”直接推出。

这对上层应用很重要。若调用者把状态版本当作实例地址，可能把请求送给错误的分支；若把实例标识当作永远不变的内容版本，又可能在回滚后误以为它仍保留最新修改。保存的是什么、运行的是谁、运行当前处于哪个状态，需要能够分别表达。

同样，克隆不是把任务历史复制到外部世界。源实例已经发送过的网络请求不会因为克隆而自动变成三笔独立且安全的业务操作。子实例继承了本地记忆，不等于远端为每个子实例建立了新的会话。第一章的外部边界，在分支场景里变得更重要，因为多个后续运行可能从同一份本地历史出发。S07

从初始化分支，还是从任务中途分支

从公共模板派生与从运行中途派生，面对的状态不同。前者的基线通常经过专门准备，尽量不包含某次任务的私有历史；后者则有意保留任务已经完成的工作，以便从当前进度继续探索。forkd 的公开资料同时描述了预热快照派生以及运行态分支的路径，但本文不把其中某项实现的性能结果推广到所有克隆。S10

设想 Agent 已经花了多轮操作完成项目分析、生成缓存和构建本地索引，接下来要尝试两种修复。若只能回到最初模板，两条分支可能重复前面的中间准备；若能保存当前状态，则可以把这个进度作为新起点。这里的价值来自共享已经完成的中间工作，而不是来自“fork”这个名称本身。

中途捕获也提高了对一致性的要求。此时程序可能正在更新文件，线程可能仍在执行，内部服务可能持有连接。快照系统必须按照自身协议取得一个可恢复的状态组合，不能让某些页面来自修改之前、另一些必需状态来自不相容的修改之后。具体协议可能在暂停时间与后台复制之间做取舍，但“可以恢复到一个明确状态”的要求不能消失。S03

如果希望源实例在捕获后尽快继续，系统还要处理源实例继续写入与后台保存之间的关系。能够缩短源实例暂停，并不等于所有数据已经复制完成；后台工作若尚未结束，制品也可能仍处于不能供任意恢复使用的阶段。关于这类路径，应区分源实例何时恢复执行与派生制品何时真正可用，不把两个完成点混为一个。

对上层任务而言，是否需要中途分支，应由重复工作的量和分支位置决定。若每次尝试都很短，重新从公共模板开始可能已经足够；若很多昂贵的中间工作确实可以共享，中途保存才具有明确收益。没有共同进度需要保留时，增加复杂的分支机制并不会自动减少任务自身的计算。

用变化量理解内存增长

写时复制最适合用“共享部分加各自变化”来思考，而不是用一个固定的克隆开销来思考。为了说明这个关系，设共享且驻留的公共页面占用为 S，第 i 个实例的私有变化页面为 D_i，实例额外运行开销为 H_i。一个简化的模型可以写成 M ≈ S + ΣD_i + ΣH_i。

这是教学模型，不是任何项目的容量承诺。S 不是虚拟机声明的全部内存，也不一定等于快照文件大小；D_i 不只包含业务主动分配的对象，还受运行过程中各种页面写入影响；H_i 则提醒我们，独立执行环境还有不能被这份共享镜像消除的开销。

这个模型解释了两种相反现象。第一批实例开始时，公共页面逐步进入驻留集合，物理占用可能随共享数据加载而增长。更多实例使用相同内容时，不必按相同幅度重复增长。但当这些实例逐渐形成各自状态，私有部分的总和又会增加。所谓高密度，依赖的是具体时刻的共享与分歧结构。

假如任务主要读取一个公共索引，只生成很小的结果，D_i 可能相对有限。假如任务不断建立大规模中间对象、重写数据或各自加载不同内容，D_i 就可能占据主要部分。不能根据模板刚恢复的占用，推断它在完整任务生命周期里都保持同样密度。

还要注意，省去重复驻留与提高可执行并发不是完全相同的目标。即使内存共享较多，CPU、存储读取或网络仍可能限制同时工作的实例数量。CoW 解决了其中一部分资源重复，并没有让每个任务的计算需求变成可共享状态。独立任务真正执行不同代码时，仍要各自消耗执行资源。

这个边界能帮助我们避免一种常见结论跳跃：从“相同初始内存可以共享”，直接跳到“任意多任务都能低成本并发”。前者是具体机制，后者还依赖任务变化量、运行开销以及其他资源约束。它们之间需要工作负载证据，而不能只靠一个快照大小推导。

用八个页面算清逻辑大小与物理占用

前面的模型可以用一个小算例落到具体数字。假设一份教学用基线恰好有八个已经驻留的页面，三个实例都映射这八页，而且暂时不计虚拟机其他开销。若三者都只读，逻辑上每个实例都有八页可用，总计二十四页视图；底层却可以由同样的八页内容提供。这两个数字分别回答了不同问题。

接着让 A 修改第一页面、B 修改第二页面、C 修改第三页面。假设每次恰好产生一页私有副本，其他实例仍然引用相应基线页，那么这部分物理内容可以由八页公共数据加三页私有数据组成，共十一页。每个实例的可见大小依旧是八页，没有因为共享比例变化就突然缩小或扩大。

这个算例不是沙箱内存基准，只用于说明为什么不能直接把各进程可见的驻留大小相加，得到整台机器对这组内容的唯一物理占用。多个进程的统计可能分别包含同一共享页。Linux 的 smaps 提供 RSS、PSS 以及共享、私有页面分类；PSS 对共享页的贡献按使用者分摊，有助于从另一个角度观察共享。S29

即便有这些统计，完整容量分析也不能只看一个进程。页缓存、其他运行时对象和宿主机开销可能落在不同统计范围内；容器、进程和整机指标也未必采用相同口径。若一项测试声称内存减少，需要先知道比较的是虚拟地址空间、进程驻留、比例分摊，还是整机实际使用。名字都带 memory，不意味着它们可以互换。

这个例子还说明了为什么观察时刻重要。刚映射完成时，某些页面可能尚未驻留；任务开始读取以后，公共页面逐渐进入内存；任务形成独有结果以后，私有页又继续增长。在这三种时刻各拍一次统计，会得到不同数字，而它们描述的都可能是真实状态。

因此，对 CoW 的理解应当同时保留两个变化方向：共享数据可能随着读取而驻留，私有数据可能随着写入而增长。前者与访问集合有关，后者与分歧有关。只用“每个克隆增加多少内存”一个常数，很容易掩盖这两段不同过程。

复制了内容，还要建立独立身份

状态继承使子实例拥有相同起点，但有些内容本来就不应该让多个独立实例永远相同。网络地址、连接关系或某些随机状态，具有与当前运行身份有关的含义。如果只复制字节而不理解这些含义，可能得到内容相同却不能正确独立工作的环境。

Firecracker 的网络克隆文档区分快照中的 guest 状态与目标宿主机需要准备的网络条件。恢复后的连接能否延续有明确限制，不应假定旧的外部网络关系自动复制为新的独立关系。对于实例交付系统来说，网络准备和身份建立仍然是恢复以外需要协调的工作。S07

随机状态也提供了一个容易理解的例子。一个确定性的伪随机生成器从相同内部状态继续，可能生成相同序列。对于需要可重复实验的任务，这可能是刻意保留的条件；对于用于安全或独立身份的随机输出，则需要满足不同要求。Firecracker 的相关文档讨论了克隆后的随机性与 VMGenID 等机制，但不能由此推断任意应用自行维护的随机发生器都会自动获得正确语义。S08

这里不是要求把快照中的所有相同值都改掉。公共数据正是我们想共享的内容。需要区分的是：某个值表达可共享的准备结果，还是表达这一次运行与外部世界的关系。前者适合保持一致，后者可能需要重新建立，或者由应用显式决定是否继承。

这也解释了为什么快照复制完成之后，系统仍可能执行一段实例化过程。它要把公共状态放到新的执行身份下，提供相应任务输入，并准备这一运行需要的外部资源。减少重复准备，不等于取消实例身份。第二章的独立性，最终仍要与第五章的领取和绑定相连。

把重复的准备组织成一棵分支树

再看一个具有共同中间过程的教学场景。十个任务都需要准备同一项目，其中五个额外需要一种数据工具，另外五个需要浏览器工具。若每个任务都从最基础镜像开始，公共项目准备重复十次，两类工具准备各重复五次。若把共同进度保存成明确状态，后续任务就可以在适当位置分支。

可以先形成项目基础状态 S，再从 S 建立两个准备分支，分别形成带数据工具的 D 和带浏览器工具的 B。真正任务分别从 D、B 出发。这里的树不是为了层级好看，而是在表达哪些前缀工作相同，应该在哪个状态版本以后才开始发生分歧。

forkd 的公开资料包含快照差异链及共同父状态的组织方式，其他分层系统也可以通过自己的制品引用表达相关关系。本文不要求所有项目采用同一格式，只强调状态来源需要明确：D 与 B 可以共享 S，但某个实际任务对 D 产生的私有修改，不能被无条件写回 S 后交给另一类任务。S10

如果每个任务的依赖都完全不同，这棵树能够共享的前缀就会变短；如果相同前缀经常变化，维护中间制品的收益也会下降。快照节点并不是越多越好，每增加一个节点，都需要保存、命名和管理它的依赖。值得固定下来的，是确实会被多个后续运行复用的准备结果。

这个场景还帮助区分模板与任务快照。D 和 B 若由受控准备产生，可以作为特定任务类别的公共起点；某个用户任务执行到一半形成的状态，则通常只属于它自己的分支历史。数据结构上都能保存，不意味着复用范围相同。是否成为公共节点，应当由内容来源和授权范围决定。

单机共享与跨机派生是两件事

在同一宿主机上，多个实例可以通过共同的内存与缓存机制复用已经驻留的页面。跨到另一台机器以后，目标机器仍需要获得相应的内容。保存格式可以传输，公共基线可以缓存，但原机器的一份物理页面不会因为实例具有共同祖先，就自动成为另一台机器的本地内存。

因此，跨机派生至少涉及制品分发和目标节点恢复两个问题。分发解决目标节点怎样获得基线及变化数据；恢复解决取得这些数据后怎样建立运行。一个系统在单机上克隆很快，并不独立证明跨节点第一次恢复也具有同样路径。若目标节点已经缓存，情况又不同于首次接触该模板。

这个区别并不削弱快照的价值。恰恰因为状态被表示为可传输制品，系统可以把准备工作与具体机器解耦。但需要承担的成本从重新初始化，转向了数据传输、缓存和恢复。下一章的分层存储，正是为了使环境越来越多时，这种制品管理不必退回到每次搬运完整副本。

到这里，我们可以准确描述“独立环境”了：每个实例的后续修改和执行由自己承担，而初始相同的部分可以在满足条件的层次共享。共享的是确定版本的数据，不是任意可变的业务现场；节省发生在尚未分歧的部分，不是对所有未来运行开销的豁免。理解这条边界，才能继续讨论如何让大量暂时不运行的环境只保留状态，而不始终保留机器。

三、环境越来越多，为什么不必把它们全部留在内存里？

等待下一条指令时，到底需要保留什么

前两章讨论了怎样建立可复用起点，以及怎样从起点派生多个独立运行。现在考虑一种不同的时间分布：环境很多，但真正执行任务的只是其中一部分。Agent 完成了一轮分析，可能要等待用户确认；一条探索分支暂时没有被选中，却还值得保留；一个开发会话在两次操作之间，也不一定持续消耗计算。

如果保留现场的唯一办法是让虚拟机一直运行，那么“以后还能继续”就和“现在必须占有执行资源”绑定在了一起。即使程序只是等待，环境的运行对象、私有内存和管理资源仍然存在。随着会话数量增加，系统可能先被大量暂时没有工作的环境占满，而不是被当前真正需要执行的任务占满。

直觉上，我们希望只保留继续工作所需的信息，把执行资源交给其他任务。这又回到了制品与实例的区别。制品代表一个可恢复状态，实例代表这个状态当前正在某台机器上运行。一个状态可以暂时没有运行中的实例，就像保存好的程序文件不要求始终对应一个正在执行的进程。

AgentENV 以快照为中心组织这类关系。模板被保存为快照，运行中的沙箱可以生成新的快照，后续实例再从已提交状态恢复。其公开概念文档区分了模板、快照和沙箱，并说明保存内容包含虚拟机状态、内存、文件系统及相关运行上下文。状态可以被保留，并不要求原运行对象永久存活。S14S15

不过，分开概念只是开始。若每次暂停都要写出完整磁盘与全部内存，保存会很重；若每次恢复都要下载整个环境，继续工作也会很重。要让大量非活跃环境真正可以按需存在，还需要一种能够表达共享基础、记录变化并支持局部读取的存储方式。

为什么从文件系统快照走向分层块数据

设想我们已经有一份公共基础镜像，某个任务在里面安装一个包，再修改几个文件。如果保存新状态时重新复制完整磁盘，原有的大量内容会再次写入。下一次任务再增加少量变化，又要完整复制一次。状态版本越来越多，物理数据却可能主要由相同内容构成。

分层表示把“完整内容”和“这次写了什么”分开。底层保存已有基线，新的一层只记录本次覆盖的范围。读取时将这些层按顺序解释，得到任务眼中的完整设备。没有变化的部分仍来自原层，发生变化的部分由较新的层提供。

AgentENV 的 overlaybd 路径按照这种思路组织块数据。它维护只读下层与一个可写上层，通过映射索引判断某个逻辑范围由哪层提供；写入进入可写上层，读取从较新内容向较旧内容查找。这里的层不是一个抽象标签，而是保存实际数据及其逻辑位置关系的制品。S13

为什么使用块层表示，而不是只记录文件名？因为虚拟机看到的是块设备，文件系统在设备之上自行管理目录、文件和元数据。运行时未必需要理解每一个 guest 文件的含义，只要能够为设备的逻辑位置提供正确字节，就能继续支持原来的文件系统视图。

这是一种边界选择：把应用和 guest 文件系统需要的完整性保留在其原有层次，把公共基础与变化的组织放在块存储层。它减少了通用运行时必须理解的应用差异，但代价是需要维护正确的块范围映射、读写顺序和快照层关系。名字叫“分层”，不意味着系统可以不处理这些细节。

从一个块的读取，看懂层的含义

用一个教学例子建立直觉。假设基础设备只有三个逻辑块，内容分别是 A、B、C。第一次保存后的变化层把第二块改成 X。此时完整设备应当读成 A、X、C，而不是只有一个 X。变化层必须与基础层共同解释，才能表示完整状态。

如果下一次变化又把第三块改成 Y，完整结果就成为 A、X、Y。读取第三块时，新层提供 Y；读取第二块时，新层没有记录，就到前一层取得 X；读取第一块时，两层都没有覆盖，最终仍从基础层读取 A。

下面用字典模拟每一层对完整块的覆盖。实际 overlaybd 处理的是范围、索引与设备 I/O，这个程序仅用于说明覆盖顺序。

def read_block(block, newest_first):
    for layer in newest_first:
        if block in layer:
            return layer[block]
    raise KeyError(block)

base = {0: b"A", 1: b"B", 2: b"C"}
first = {1: b"X"}
second = {2: b"Y"}
layers = [second, first, base]
assert [read_block(i, layers) for i in range(3)] == [b"A", b"X", b"Y"]

程序里最重要的是 block in layer，而不是返回值是否“看起来为空”。若最新一层有意把某块写成零，这仍然是有效覆盖，不能因为内容为零就去读取旧值。实际分层格式需要能够区分没有覆盖与明确写入某种内容；AgentENV 架构文档中的映射包含相应的零值语义。S13

这个例子还揭示了删除与缺失的区别。文件系统中的删除最终会表现为设备上的一些更新，分层存储不能把“新层没有记录”简单解释成“旧内容不存在”。它只是表示需要向下查找。要改变任务看到的设备内容，就必须有足以表达这个变化的记录。

对于跨越多个块或区段的读取，真实系统还要组合不同层提供的范围。本文不复述索引的数据结构字段，但这些索引并不是可有可无的优化：没有它们，就不知道一段逻辑读取应该向哪里取数据。分层能避免整份重写，是因为系统承担了以后正确解释各层的工作。

读取横跨几个版本时，怎样拼回正确内容

前面的字典示例把每个块当作整体覆盖，便于理解新层优先。真实请求可能跨越多个映射范围，同一段读取的不同位置由不同层提供。因此，索引还要帮助系统把读取拆成有确定来源的片段，再按原顺序组合。

用八个字符表示一段教学数据，基础内容是 AAAABBBB。第一层把中间四个位置覆盖为 xxxx，完整结果成为 AAxxxxBB。第二层再把其中两个位置改为 YY，完整结果成为 AAxYYxBB。这是逻辑范围示例，真实块设备还需要满足自己的对齐与 I/O 约束，不能照着八个字符推断设备写入粒度。

现在请求一次读取全部内容，最新层只能提供中间的 YY，不能提供整段八字符。系统还要从前一层取得两侧仍然有效的 x，从基础层取得首尾的 AA 与 BB。如果只是找到“第一层有这个请求的一部分”，就把整个请求交给它，会丢失其余位置的正确来源。

这解释了为什么分层存储需要逻辑范围与实际数据位置的映射。索引不仅回答某个块是否被更新，还要表达覆盖边界及对应内容。AgentENV 的 overlaybd 路径通过区段映射组织这些关系，读取按新旧层及映射范围解释，写入再更新上层的相应记录。S13

增加这些索引会产生额外元数据，但它们换来的是不必每次重写完整设备。若所有历史都先合并成一个文件，读取端不需要跨层拼接，却要提前支付合并工作。两种办法并非谁无成本，而是把计算放在保存、整理还是实际读取时完成。

这也帮助理解压缩与分层的区别。压缩尝试用更少字节表达某一份数据，分层尝试不再次保存已有且未被覆盖的内容。它们可以结合，但不是同一件事。一个压缩得很好的完整副本，仍可能与另一个完整副本重复；一组增量层也可能包含难以压缩的新内容。

保存快照是在固定哪一段变化

当前可写层随着运行持续变化，不能直接同时充当一个永远不变的快照。否则任务继续执行以后，已经对外发布的“过去状态”也会跟着改变。快照需要把某个时刻以前的变化固定下来，并为之后的新写入安排另一个位置。

AgentENV 的主要路径会封存当前可写层，使其成为新的只读下层，再打开一个新的可写上层。这样，旧层代表已经完成的一段变化，新上层接收后续运行的更新。所有仍引用旧快照的恢复，都应该继续看到相同内容，而不是源实例最新写入的内容。S13

用刚才的例子看，基础层与 first 被一起引用时，可以表达状态 S1。源实例继续运行，向一个新层写出 second，形成状态 S2。引用 S1 的任务仍看到 A、X、C，引用 S2 的任务看到 A、X、Y。两个状态共享前面的基础，却有不同的最新覆盖集合。

这里的“共享”首先是共享不再修改的历史层，而不是共享一个仍然变化的上层。不同分支可以从 S1 出发，各自建立自己的可写层。A 分支的新写入不会进入 B 分支的上层，公共下层也不会被它们任意修改。这样，第二章讨论的独立变化在持久化表示中也有了对应结构。

值得注意的是，创建快照和暂停沙箱不是同一个业务动作。快照可以生成一个以后可用的状态版本，而源实例随后继续工作；暂停则意味着当前执行暂时停止，并按照运行时流程释放相应资源。二者可能共用捕获与提交步骤，但调用者对源实例的期待不同，不能仅因为都涉及快照就混用。S15

同样，“新层文件已经产生”和“完整快照可以恢复”也不必是同一个时刻。需要的元数据、基础层引用、机器状态及其他资源内容都应具备可用条件。这是根据恢复所需对象得到的要求。至于某个实现何时返回、是否后台上传，应查它具体的提交语义，不能从存在一个文件就推断所有阶段已经完成。

虚拟机怎样使用这些分层文件

到这里，状态已经变成若干层和索引，但虚拟机并不会直接遍历这些层。对 guest 而言，它需要一块能读取和写入的设备。运行时要在逻辑设备接口与分层数据表示之间建立连接，否则上层仍然无法把这些制品当作运行环境使用。

AgentENV 使用 Linux 的 ublk 机制，将用户态实现的块存储暴露成块设备。内核负责与块设备使用方交互，用户态服务收到请求后，再根据 overlaybd 的映射查找相应内容，完成读取或写入。这让分层组织能够在用户态实现，而使用设备的虚拟机仍沿块设备路径工作。S13S16

可以跟踪一次 guest 读取。guest 文件系统需要某段设备内容，请求到达宿主机上的相应块设备；ublk 路径把请求交给用户态后端；后端查分层索引，决定哪些字节来自哪层；获得内容后完成 I/O，guest 再继续原来的操作。每个环节都在回答不同问题，没有哪一个名字能够代替整条过程。

为什么不在恢复前把所有层先合并成一个完整文件？这当然是一种可以想象的替代方案，读取端会更简单。但合并需要提前读取和写出大量内容，即使实例最终只访问其中一部分。把分层解释保留到读取路径，就有机会避免这段完整材料化工作，同时把索引与数据获得的成本留给实际访问。

这个选择并不意味着读取免费。层查找、数据解压、缓存缺失以及底层 I/O 都可能发生。设计取舍在于，是否值得为使用者真正访问的部分做这些工作，以避免每次准备完整副本。访问很少时，按需组织有明显的工作量依据；每次都遍历完整设备时，就要重新判断预处理与访问路径的成本关系。

内存也可以沿块设备路径恢复

磁盘使用块设备容易理解，内存为什么也出现在这里？因为暂停后的内存不再是正在执行的物理 RAM，而是一份保存的数据。只要能够按照逻辑偏移返回正确字节，它就可以由一种可映射的后端提供，供虚拟机建立恢复后的内存视图。

AgentENV 当前的内存恢复路径使用由 overlaybd 支撑的只读 ublk 设备，作为 Firecracker 的文件型内存后端。Firecracker 映射这个设备，在第一次写入页面时形成私有匿名内存，底层只读设备不接受这些任务私有写入。这个路径不是 E2B 前面描述的用户态 userfaultfd 供页路径，虽然两者都可以实现按需恢复。S13

这项区别值得明确，因为相同目标并不要求相同机制。一个实现可以专门处理缺页事件，另一个可以让内核文件映射与设备读取路径提供页面。它们需要观察的队列、缓存和错误路径并不完全相同。如果只因为二者都说“懒加载内存”，就按同一张调用图理解，后面的成本解释会发生偏差。

AgentENV 还让使用同一快照的实例共享一个内存设备，并以引用计数管理其使用。这使宿主机页缓存能够围绕同一底层对象复用已读取的页面。这里共享设备的意义不只是少创建一个设备编号，更重要的是使相同状态经过同一个可复用的数据对象进入内存路径。S13

但不能把这个事实扩大成任意两个内容相似的快照都自动共享全部内存。相同基线、不同变化层、不同设备对象以及各实例已经形成的私有页面，会影响实际共享。本文能确认的是该实现对同一快照设备的复用机制，不能凭它推导未核实的任意跨版本去重。

再次回到制品与实例：制品侧提供不可变的内存视图，实例侧建立自己的可写执行状态。读取可以从共同内容获得，写入形成实例自己的变化；当实例暂停，这些变化又被提取出来，成为下一份可保存状态的一部分。

内存中的变化怎样重新成为增量层

如果实例已经通过私有页面积累了变化，下一次暂停时就要把必要内容保存下来。此时不能只保存原来的共享后端，因为它有意保持不变，不包含任务的新状态。也不必因此放弃增量，重新写出全部内存。

AgentENV 的架构文档描述了这样的路径：Firecracker 生成相应机器状态，运行时查询脏页及存在页面范围，再使用 process_vm_readv 读取选定内存，直接构造新的 overlaybd 内存层。父层与新层合起来，表示恢复所需的完整内存内容。S13

这里的“脏”是内存管理意义上的变化，不是业务上文件是否被修改。程序只是在内存中调整了对象，仍可能产生需要保存的页面；某个文件内容没有变化，也不意味着解释器或服务内部没有新状态。因此，不能用项目目录里有几个修改文件来直接估算内存快照的变化量。

同样，增量捕获不只是“只保存用户认为重要的变量”。运行时仍要维持机器级恢复所需的完整性。选择哪些页面可以由父层提供、哪些页面必须从当前实例取得，要遵守它的内存与快照协议。省下的数据来自已有状态可以正确继承，而不是任意跳过暂时看不懂的内存内容。

当任务主要读取共享状态、只形成少量私有变化时，新层有机会较小。当任务反复改写大量页面，保存的新内容自然增加。这个成本与第二章的私有内存增长对应：运行阶段的分歧，并不会在持久化时神奇消失，只是被转成可以继续引用的状态制品。

缓存让状态不必全部待在本机

到目前为止，分层减少了重复存储，但如果要求每台机器预先准备所有层，环境种类一多，本地磁盘仍会承受很大压力。AgentENV 将本地存储作为有容量限制的缓存，按实际访问保留热内容，让状态集合不必完整常驻每台计算节点。S17

这里的逻辑与内存按需加载相似，但不要混淆两种资源。内存按需加载决定哪些页面现在驻留 RAM；本地存储缓存决定哪些制品数据现在位于这台机器附近。某份内容在远端存在，不等于已在本地磁盘；已经在本地磁盘，也不等于已经进入页缓存。一次恢复会经过哪一层，取决于当前数据位置。

以一个假设时间线说明。任务 A 恢复时读取公共层的一部分，将其带入本地缓存和相关内存路径；不久后任务 B 使用相同内容，就可能复用这些数据。随后许多不同环境进入，缓存容量不足，较冷内容被淘汰。等任务 A 的后续分支再次需要它时，便可能重新获得。共享机会仍然存在，但不能假定它永远命中。

这解释了为什么需要同时看环境数量与工作集合。系统登记了一万个可恢复环境，并不表示它们的所有字节都要位于本机；当前一批任务反复使用相同少量基线，也不等同于访问一万个互不相同的大环境。决定本地压力的是实际需要留近的数据，而不仅是逻辑状态的个数。

缓存还带来一种重要失败边界：缓存可以被淘汰，因为它应当有其他可靠来源；尚未持久化的唯一变化则不能被当作普通缓存随意丢弃。对一个存储中心的系统来说，哪些数据已经提交、哪些只是临时副本，需要明确区分。否则“缓存有界”会错误地变成“状态可以被随机删除”。这里是通用设计要求，不是声称所有实现自动完成了同一种耐久性策略。

从暂停到恢复，沿一次交接看数据在哪里

现在把本章各部分放进一次完整的状态交接。下面是根据前述机制组织的教学流程，不是某个项目保证的固定 API 调用顺序。设实例 A 正在运行，使用公共基础层和自己的可写变化，接下来希望暂停，稍后可能在另一个合适节点继续。

第一步是取得与运行时协议相符的捕获状态。需要知道本次机器状态、内存变化与设备数据视图相互对应。这个阶段结束后，系统拥有能够描述某个明确运行点的材料，但材料是否已经达到所要求的持久化范围，是另一个需要确认的条件。

第二步是形成可引用的快照。它不只是新产生的数据层，还包括足以找到基础层及其他必要内容的引用。假设内存变化已经保存，但它依赖的基础镜像只存在于即将被清理的临时位置，那么“新层保存成功”并不能让目标节点完成恢复。完整性需要按全部依赖判断。

第三步才是按照暂停语义结束当前执行，并释放不再需要的运行资源。哪些缓存继续保留，取决于后续访问价值与容量政策；它们可以帮助下一次恢复，但不应成为没有说明的唯一可靠副本。这样，实例离开运行集合与状态仍然可恢复，才是能够同时成立的两件事。

恢复时，目标节点先取得快照引用及相应配置，再为需要的状态建立读取路径。命中的本地数据可以直接使用，未命中的数据按支持路径取得；内存与磁盘映射建立后，运行从保存点继续，后续访问仍可能触发更多数据读取。最后，实例还要通过必要就绪条件并接入访问路径。

这条流程揭示了几个容易混用的完成点：捕获结束、快照满足保存要求、旧执行被释放、新执行能够继续、业务入口能够使用。它们可以在实现中组合，也可以部分异步，但各自代表的条件不能被省略。一个接口返回什么状态，应当能对应其中明确的承诺。

如果系统只要求在原节点恢复，它可以利用更局部的数据条件；如果要求原节点失效后仍能继续，就需要保证所需状态不只留在那里。两种服务目标会影响保存路径。不能先只完成较弱条件，再用“已经有快照”代替较强的恢复保证。

同一批唤醒为何可能出现不同等待

考虑三类处于暂停状态的环境。第一类最近刚运行过，所需数据仍在本地和页缓存中；第二类在本地有制品，但相关页面已经不驻留；第三类甚至需要重新从较远存储取得某些层。它们都叫作从快照恢复，实际经过的读取路径却不一样。

如果把三类请求的时间混成一个数字，就难以解释变化来自哪里。第一类可能主要支付运行重建，第二类还要完成本地读取，第三类则额外承担数据获取。这里没有给出性能优劣排序的实测，只是沿着数据位置说明可能增加了哪些工作。

多个环境同时唤醒时，还要考虑它们是否读取共同内容。如果共享同一快照设备及缓存路径，有些读取可以复用；如果请求来自大量不同状态，缓存命中机会可能下降。AgentENV 对同快照内存设备的共享，为前一种情况提供了具体机制，但不能据此推导任意环境集合都有同样收益。S13

这就是为什么环境规模不宜只用“保存了多少个沙箱”描述。运行数量、同时唤醒数量、共同基线比例和当前数据位置，分别对应不同工作。把状态与实例分开以后，平台得到更大的调度空间，同时也需要更准确地描述真正活跃的数据集合。

层越来越多时，读取也需要付出组织成本

分层避免了每次完整复制，却把一部分复杂性留在未来读取中。状态经历很多次保存后，某段内容可能来自很早的基础层，另一段来自最近一次修改。如果每次读取都要反复遍历许多层，索引与定位工作就可能变得重要。

实际系统可以通过索引、缓存或不同的整理策略缩短查找路径，但这些动作本身也有成本。把多层合成为较平的表示，需要读取既有内容并产生新的组织；始终不整理，则可能让恢复与访问承担更多历史解释工作。本文不假定 AgentENV 必然采用某个未核实的自动压实策略，只说明这类分层表示自身引入的取舍。

同样，删除一个状态版本不一定意味着所有它引用的层都可以立即删除。其他状态或运行实例可能仍依赖这些内容。共享减少物理重复，也使生命周期从“一份状态对应一份独立文件”变成“多个状态引用一组基础数据”。删除必须针对引用关系，而不能只根据某个业务对象已经结束来行动。

可以用分支例子理解：S1 是两个后续状态 S2 和 S3 的共同基础。用户不再需要直接恢复 S1，但 S2、S3 仍可能需要其中的数据。只删除一个可见名称，与回收底层数据，是不同层的动作。文件系统 reflink和显式分层在具体引用管理上可以不同，但共享内容需要在仍被使用时保持可用，这个条件一致。

因此，状态制品越多，系统越需要把可见版本、实际数据和正在使用的引用分开管理。否则省下的复制成本会转化为难以判断的删除风险。这里的深度不在于引入更多存储术语，而在于看见一个设计消除重复之后，必然承担了什么组织工作。

暂停何时有意义，不能只看恢复速度

如果环境几乎一直在工作，频繁暂停再恢复可能增加没有必要的保存与读取。如果环境有明显的等待间隔，保留全部执行资源则可能浪费占用。暂停策略因此需要同时理解空闲时长、保存成本、恢复成本和下一次任务的等待要求。

这些量不能随意相加。内存占用是容量或容量乘时间，保存与恢复还有 CPU、I/O 和延迟。一个平台若要把它们转换成统一成本，需要自己的资源权重与服务目标。不能把“保存花一秒”与“占用一 GiB”直接比较，得出一个看似精确的休眠阈值。

更稳妥的机制判断是先找明显条件。环境长期不活跃，又需要保留较多现场，状态与实例分离有明确动机；环境持续被访问，则反复迁入迁出可能抵消收益。快照变化量小、缓存常命中，与快照巨大、每次冷读，也会形成不同取舍。

AgentENV 的设计值得理解的地方，不是“暂停可以无限超售”之类的口号，而是它把环境表示为可以独立保存、共享并按需读取的状态。这个表示使资源调度不必永远跟着会话数量走，但也把部分工作转移到存储和缓存。是否适合某种任务，要沿着这些变化后的工作检查，而不是只看一个恢复时间。

第三章到这里得到的结论是：保存一个世界，不需要这个世界始终在运行。只要状态能够被准确表示并重新接回执行，环境就可以在制品与实例之间转换。不过，既然能保留如此完整的状态，我们还需要问另一件事：下一次执行真的应该继承这些内容吗？这个问题决定了下一章的回收边界。

四、任务结束后，应该保存现场，还是重新开始？

完整保存有时正是错误的继承

前面三章一直在寻找值得保留的工作结果。现在反过来问：一个任务结束以后，它留下的所有状态都值得交给下一个任务吗？如果后续操作属于同一项工作，继续使用原来的变量、文件和进度通常很自然；如果后续操作来自另一个独立任务，这些内容可能成为污染。

以独立执行测试为例，我们希望两次尝试从相同基线开始。第一次尝试可能修改配置、启动辅助服务，还可能在失败之前留下一部分临时数据。若第二次尝试接着使用这个现场，测试结果就同时依赖第二次代码和第一次留下的状态。这样得到的结果不再只回答第二次方案是否成立。

这里“污染”不必是恶意行为。正常程序也会产生缓存、后台进程和局部结果。一项任务因异常提前退出时，原本安排在最后的清理步骤可能没有执行。即使每个程序都没有攻击意图，继续复用任意结束状态也可能使后续任务失去可重复的起点。

因此，任务结束后的设计问题不是“能否保留状态”，而是“下一项工作允许继承哪些状态”。公共依赖与可信初始化可以继续复用，任务私有变化则需要按语义保存或丢弃。第三章提供了保存机制，本章要为保存与丢弃划定边界。

为什么删除工作目录并不等于重置环境

最容易想到的清理方式，是删除任务创建的目录，再准备一个空目录交给下一个任务。如果状态确实只存在于这些文件里，这种方法可能足够。但通用执行环境中的状态并不只由可见目录组成。

程序可以在内存里保留变量，也可以启动其他进程。打开的文件描述符代表一段已经建立的资源关系，不能仅凭某个路径现在不存在，就断定所有相关访问都结束。网络连接、挂载和内核维护的对象，也不一定随工作目录清空而消失。Linux 的文件接口将文件路径与已经打开的引用区分开，正是这种区别的一部分。S28

假设一个任务启动后台服务，主进程很快退出，清理程序随后删除临时目录。如果后台服务仍然存在，它可能继续持有旧文件、监听端口，或者生成新的写入。下一个任务遇到的环境，仍然受到上一个任务的活动影响。问题出在清理边界没有覆盖仍然活跃的状态，而不是删除命令执行得不够快。

即使能终止已知子进程，也需要明确“已知”从何而来。只根据最初启动的进程标识推断整个环境已经安静，容易漏掉执行树中的其他活动。通用沙箱通常需要在更完整的执行边界上管理进程与资源，而不能要求每一种用户程序自觉把所有后续对象登记给清理脚本。

这并不意味着应用级清理永远无效。对行为明确、状态范围有限的可信服务，显式重置几项对象可能更便宜。但如果运行任意代码，清理程序必须知道的行为范围会扩大。与其把任务做过的每一步都逆向撤销，另一种方法是销毁它能够影响的运行环境，再从已知基线建立新的环境。

gvisord 把重置放到沙箱内核边界

gvisord 管理由 gVisor 提供的执行环境。gVisor 的隔离方式与 Firecracker 微虚拟机不同：它通过用户态实现的系统接口与相应隔离机制承接应用的系统调用，而不是让每个实例运行同一种 KVM 微虚拟机。这里讨论它，是因为重置边界的思路与前面状态复用问题直接相关，而不是把两种隔离技术视为同一类实现。S18S21

在 gvisord 的常规 runsc 路径中，一次执行获得自己的沙箱内核。执行完成后，容器及相关内核状态被销毁，再从检查点恢复新的实例。任务下一次看到的起点来自预先准备的检查点，而不是上一次执行后的现场。它复用的是可信基线，不是任意任务留下的运行结果。S18S19

这个设计改变了清理问题的范围。系统无需理解某个 Python 变量表示什么，也不需要为每一种进程行为编写业务逆操作。只要这些变化位于被销毁的执行边界内，它们就随这次运行一起结束。重置依赖的是隔离边界和重建流程，而不是用户程序最后是否调用了某个清理函数。

不过，这个说法必须限定到该边界内。若任务被允许写入外部存储，销毁内部内核不会自动改回外部字节；若某个资源由宿主机其他服务持有，也需要相应的生命周期管理。内核重建可以覆盖一类状态，但不会把整个系统中所有发生过的变化都纳入回滚。

gvisord 也描述了能够保留宿主机 sentry 进程、重置其中内核状态的路径。对本文的认识目标，重要的是任务私有的内核运行状态被重新建立，而不是操作系统里是否恰好复用了同一个宿主进程标识。基础说明仍以更直接的销毁再恢复路径为准，不把实验性路径的性质扩大到所有部署。S18

为什么重建 Sentry 中的状态能结束一组 guest 对象

“重建内核”听起来很抽象，可以从程序读取自己进程编号这个操作理解。普通程序调用 getpid()，需要系统告诉它当前进程身份。gVisor 的架构说明中，这个请求由 Sentry 根据自己维护的 guest 进程表回答；guest 看到的进程对象，并不简单等于宿主机上同编号的原生进程。S21

文件描述符、信号和网络等接口也需要相应的 guest 侧状态支持。应用以为自己正在和一个 Linux 环境交互，Sentry 为这些调用维护必要对象，并在受约束的范围内使用宿主机能力。因此，销毁这一组沙箱内核状态，可以结束其中的进程关系和资源视图，而不必逐个理解应用业务变量。

这个说明还避免了一个误解：不能把 gVisor 只理解成“给系统调用加一层过滤”。它需要实现应用所见的相关内核接口与状态，未实现或不支持的能力有自己的边界。重建之所以覆盖较广运行状态，正是因为这些状态由沙箱内核统一承载，而不只是由一份允许调用名单控制。S21

对于管理者，检查重置是否成立应当看这组任务状态是否被重新建立，而不能只看宿主进程编号是否变化。若一种受支持路径保留外部进程壳却重置内部内核，对 guest 而言仍可能是新环境；若只是启动了一个新业务子进程，却继续共享旧的可变服务，任务状态也未必彻底分开。需要追踪的是状态对象及其归属。

这也说明不同底座可以采取不同回收方式。微虚拟机通过自己的 guest 内核与设备状态形成边界，gVisor 通过应用内核状态形成边界。它们不具有完全相同的实现或兼容性，但在本章的问题上，都需要回答哪些私有变化随着一次执行结束而被丢弃。

什么时候应用自己的重置函数已经足够

把重建环境讲清以后，也应当给较轻方法留下明确适用范围。若一个服务只执行固定逻辑，维护的可变对象有限，并且能够完整定义每轮请求结束后的状态，那么应用自己的重置可能比重建整个执行环境更合适。它省去了无关初始化，只恢复业务确实改变的对象。

例如，一个可信服务的请求只在独立的数据结构中计算，结束后丢弃该结构；公共索引保持只读，其他服务状态不随请求变化。这里的任务隔离主要依赖清晰的应用状态设计，未必需要每个请求都重建沙箱。选择较重边界，应该有超出这个封闭状态集合的实际需求。

通用 Agent 执行的难点在于，可变状态集合不一定由平台事先掌握。任务可以加载不同库、启动工具和改变自己的文件。平台若试图为每一种行为编写重置函数，就需要持续理解这些行为的全部后果。此时，统一丢弃执行环境可以减少对应用内部细节的依赖，但要支付重建及状态交接成本。

两种方法解决的是不同约束下的同一问题：下一项任务能否得到规定的起点。应用级重置的前提是可变范围足够明确，环境级重建的前提是任务变化确实被相应隔离边界覆盖。不能只看到前者步骤少就认定更优，也不能只看到后者范围大就忽略不必要的成本。

这个取舍还与任务频率有关。如果单次工作极短，重建成本可能占较大比例，值得重新检查是否真的需要任意代码环境；如果任务本来就需要广泛工具和独立系统状态，应用层重置可能难以完整表达其边界。应当先确认工作形态，再选择让哪一层负责丢弃状态。

执行入口与管理进程为什么分开

gvisord 将宿主机上的管理守护进程与沙箱内的执行入口分开。管理端掌握池、运行时调用及资源管理，沙箱内的入口负责接收任务、执行并返回结果。两者位于不同职责与权限范围中。S18

从重置角度看，这个分离很有意义。用户代码所在的环境可以被销毁，负责决定何时重建、从哪里重建以及交给谁的管理过程不应跟着消失。否则每次任务结束，连维持下一次执行的控制逻辑也要由任务环境自己恢复，职责会相互缠绕。

从状态继承角度看，执行入口应当只得到完成任务所需的信息，而不需要了解宿主机上的快照路径、池状态或其他实例。这样，任务环境保存和恢复的是它自己的运行上下文，管理端保留的是资源与归属关系。两类状态虽然协作，却不能因为一次快照就被混成一个共同可写空间。

这个分离本身不是无条件的安全证明。权限、接口和实际运行时仍然需要正确配置。它解释的是为什么管理状态不应该由任意任务代码直接维护，以及为什么清理任务环境时还能由外部管理者继续协调。不能把一张组件图的分离直接写成所有攻击路径都已被排除。

还有一个与第一章相呼应的细节：gvisord 的默认执行入口可以启动用户代码子进程。即使检查点恢复了已经准备的 gVisor 环境，也不能据此断言每个 Python 任务都直接复用一个已导入全部业务模块的解释器。执行方式决定了究竟继承哪段初始化，仍然需要沿入口核对。S19S20

任务结束到可再次领取，中间有一段真实工作

现在跟踪一个实例被两项任务先后使用的过程。任务 A 正在执行时，这个实例当然不能交给 B。A 返回结果之后，旧进程和运行环境还需要回收，新环境还需要恢复。这个阶段既不是正在处理 A 的正常业务，也不是已经能够交给 B 的可用状态。

gvisord 用 ready、running、draining 区分这些阶段。领取使可用实例进入运行，完成使其进入回收；根据运行时路径进行重置或销毁重建后，实例才重新成为可用成员。若回收发生错误，会走销毁并替换的路径，而不是仅把旧状态标签改回 ready。S18

可以用一个简化时间线说明：A 在时刻 t1 结束业务，管理端在 t2 开始清理，在 t3 完成新环境恢复。若 B 在 t1 与 t3 之间到达，即使系统里仍看得到那个宿主进程或实例记录，也不能把它当作现成库存。B 需要另一个 ready 实例，或者等待供应真正完成。

这就是为什么“归还”与“再次可用”应该分开理解。gvisord 的 complete 可以触发后台回收并返回，调用者收到完成响应并不表示所有重建工作都已经结束。异步回收减少了调用者等待清理的时间，却没有减少清理本身所需的工作。S20

如果只统计池里一共登记多少实例，就看不出这个区别。十个实例中八个在运行、两个在回收，与十个都处于 ready，对新请求提供的能力完全不同。生命周期状态不只是日志标签，而是决定哪些对象能够安全交付的业务条件。

同样，健康探针应该对应它所承诺的能力。管理进程还活着，只证明管理接口可能可以响应；有可用实例，才说明至少某种请求可能得到供应；符合某个特定配置的可用实例，又是更具体的条件。不能用一个最宽泛的存活状态代替所有层次的就绪。

只读公共内容与私有写入需要一起设计

要让重新恢复的实例获得可信基线，底层共享内容也必须维持相应条件。如果多个任务通过共享可写目录改变了所谓公共依赖，即使每次都重建内核，下一次恢复仍可能读取被之前任务改过的文件。

gvisord 将执行入口和依赖缓存以只读方式挂入沙箱。根文件系统本身是否只读，则取决于检查点的 OCI 配置中的 root.readonly，不能把所有根目录都自动视为只读。这个实现细节提醒我们：内核重置与存储写入边界必须配套检查。S19

一个常见的教学划分，是把已经构建并确认可以共享的依赖放在只读基础中，把任务生成的文件放到独立可丢弃位置。任务结束时，私有部分随生命周期回收，公共基础不受这次写入影响。这样，重建才不仅更换了一组进程，也恢复了正确的可见输入。

如果确实需要跨任务积累缓存，则要说明这个缓存属于什么信任范围。由受控构建过程产生、经过确认后发布的缓存，与任意任务都可以写入并立即被别人使用的目录，不是同一个状态来源。把后者称为性能优化，并不能消除它对后续执行内容的影响。

这里可以看到，公共基线与任务产物之间需要一个有语义的转换过程。某次任务产生的结果，若要成为以后任务的共同输入，应当经过应用定义的保存或发布，而不是因为它碰巧写在共享目录里就自动升级为公共状态。具体检查方式取决于业务，沙箱的内核重建不能替业务作出这个判断。

哪些输出应当在销毁之前被保存

丢弃任务现场，并不意味着任务的所有结果都应该消失。代码执行可能生成日志、补丁、图片、测试报告或其他需要保留的产物。如果这些内容只存在于即将销毁的私有环境中，上层就需要在回收边界之前决定如何取得它们。

gvisord 的一键执行路径会收集执行结果，再回收实例。这说明结果交付与环境回收是同一流程中的两个不同动作。输出已经返回给调用者，并不要求整个执行环境继续存在；反过来，环境可以恢复，也不能代替对输出是否已经保存的确认。S20

以代码修复为例，任务结束后真正需要保留的可能是补丁和测试记录，而不是全部解释器内存。如果上层把这些结果明确提取出来，就可以丢弃其他运行现场。若后续还要继续人工调试，则可能选择保存完整环境。两种选择对应不同的后续操作，没有必要让所有任务都采用最重的保存方式。

输出与回收之间的失败也需要业务定义。假设计算成功，但产物上传失败，系统不能简单把“任务程序退出码为零”当作整个交付已经完成。是保留实例以便重试提取，还是从已保存状态重新执行，需要上层根据产物语义决定。这里讨论的是通用工作流要求，并不声称 gvisord 自动实现了完整的产物提交协议。

这个例子让“任务结束”变得更准确：程序停止执行、需要的结果已经保存、实例可以被丢弃，可能是三个不同事件。设计中把它们明确分开，才能既不长时间保留无用环境，也不在结果尚未交付时过早销毁唯一副本。

一轮请求与一项任务不一定重合

对一次脚本执行，一次请求可能就是完整任务。对 Agent 的多轮工作，一次任务可能包含几十次文件读取、命令执行和结果观察。若每次工具调用之后都回到初始快照，Agent 刚刚产生的文件和变量就会消失，任务无法连续推进。

因此，重置边界应当跟随工作语义，而不是机械地跟随 HTTP 请求数量。假设 Agent 先创建文件，再运行测试，最后读取报告，这三次操作需要看到同一项工作逐步形成的状态。只有任务真正结束，或者应用明确要求重新尝试，才应当回到公共基线。

gvisord 的 execute 路径允许先领取一个实例并取得租约，随后由调用者使用，最后通过 complete 结束占用。这个接口把“一键执行后回收”扩展为“持有环境直到上层宣布完成”，适合需要更明确生命周期的调用方式。S20

不过，持有实例与持有解释器仍然不是完全相同的事情。同一个沙箱可以在多轮操作中保留文件，而每轮命令仍启动新的进程。如果需要保留 Python 全局变量，还要有能够维持同一解释器的执行入口。默认执行入口的请求处理方式也不能被泛化为任意多轮持久协议。S20

从这里可以形成一张更清楚的状态范围：命令结果属于某次执行，进程变量属于那个进程，文件属于相应存储视图，租约表达对实例的一段占用，快照表达可恢复版本。将它们分别理解，才能知道某个“保持会话”的承诺究竟保持了什么。

租约超时解决失联，不等于业务事务回滚

如果调用者领取环境以后崩溃，管理端不能无限等待它归还。gvisord 为租约设置超时，到期自动触发回收。这个机制让失去调用者的运行环境有一个结束条件，避免仅依赖正常路径上的 complete。S18S19

可是，超时不自动证明任务从未产生结果。调用者可能在网络中断前已经提交执行，任务也可能在超时前完成了一部分工作。管理端看到的是占用关系到期，而不一定知道业务上哪些外部操作已经成功。因此，租约回收处理资源生命周期，不能代替业务去重或事务语义。

设想任务把一份记录写入外部服务，然后在返回结果之前失联。沙箱被回收以后，上层重新从干净快照执行，外部服务中的第一份记录仍可能存在。环境重置只让本地状态重新开始，不会自动告诉外部服务这次重试应当替换还是重复原记录。

这也是为什么需要把“干净重试”与“没有重复副作用的重试”分开。前者关注下一次本地执行的起点，后者关注跨执行的业务效果。对于会改变外部系统的任务，应用需要自己的操作标识、状态确认或其他协议。具体采用何种方法超出本文范围，但这段因果不能因为沙箱提供了快照就被省略。

对纯计算任务，情况可能简单得多：输入固定、结果可重新生成、没有外部写入，重建后重试主要承担重复计算成本。由此可见，同一种租约超时机制适合怎样的重试，仍然取决于任务是否产生了超出沙箱边界的变化。

回到快照，并没有把外部世界倒回去

这个边界值得再用一次完整过程说明。假设 Agent 在本地文件中记录“尚未提交”，随后向远端提交一个变更，再把本地记录更新为“已提交”。如果在远端已经成功、本地尚未更新时捕获或中断，恢复后的本地状态可能仍表示尚未提交，但远端事实已经不同。

无论是继续这个快照，还是销毁后从更早基线重试，都不能仅凭本地状态决定远端从未接受过操作。保存机制准确地保留了它捕获的本地世界，问题在于业务操作跨越了未被共同捕获的边界。这不是把快照精度提高一点就能独立解决的事情。

同样，如果任务获得一个共享可写挂载，并在其中修改文件，重建只读根环境不会自动恢复该挂载。若应用希望整个工作回到旧状态，就需要让相关存储也具有与之匹配的版本与恢复协议。只恢复部分状态，应该明确承诺恢复的就是那一部分。

因此，设计“每次执行独立”时，应当问独立性覆盖了哪些对象。进程与内核、私有文件、附加卷、远端服务，各自可以有不同的生命周期。适当的沙箱边界能够隔离大量运行状态，但不是整个业务系统的时间机器。

沿一次多轮任务选择保留与丢弃

下面把这些选择放进一个完整的教学场景。某个 Agent 先读取项目并建立自己的分析笔记，随后修改代码、运行测试，再等待用户确认是否采用补丁。这个过程中有公共准备，也有只属于这项工作的进度，最后还有需要长期保存的结果。

项目工具和公共依赖可以来自可信模板。任务第一次领取实例之后，分析笔记、临时文件和正在使用的解释器属于任务私有状态。第二轮命令应当继续看到它们，否则前一轮工作会丢失。这一阶段结束的是一次操作，而不是整项任务，所以不应该仅因工具调用返回就立即回到公共基线。

等待用户期间，若平台选择暂停，可以将这项任务的现场保存为私有快照，再释放执行资源。恢复以后，应当继续这项工作，而不是把私有快照当作所有新用户的共同起点。这里的状态保存承接第三章，归属与访问则要继续遵守原任务的范围。

用户决定采用补丁后，上层明确提取补丁与必要结果。如果不再需要现场，就结束租约并回收私有环境。下一项无关任务从可信公共模板开始，不继承分析笔记和上一次运行留下的进程。这样，同一个平台在不同阶段同时使用了延续、暂停、结果保存与重建，没有必要给整个产品贴一个永久“有状态”或“无状态”标签。

若用户希望继续调试，则可以保留原任务或其快照。这个决定延长的是特定工作现场的生命周期，不应自动延长所有无关资源。比如最终结果可以长期保存，而运行实例只在需要交互时存在。将结果、私有快照与实例分开，才能为它们选择不同保留时间。

这个场景也说明为什么租约不是快照的同义词。快照让状态能够存在，租约决定当前谁能使用执行实例。一个没有运行实例的私有快照仍可被保留，一个正在执行的实例则必须有明确归属。只有把两者分开，暂停才不会被误解为取消任务，回收也不会被误解为必须删除所有结果。

可信基线与有价值现场，可以同时存在

经历这些边界以后，保存现场与回到基线不再互相矛盾。一个多轮 Agent 在任务内部可以保留状态，暂时等待时可以暂停到快照；当需要比较独立方案时，可以从明确版本派生；当任务结束且不再需要现场时，再丢弃私有运行状态。

可信基线的价值是给新工作提供可重复起点；任务快照的价值是保留某次工作的进度。它们的内容来源与复用范围不同。不能把任意任务快照无条件放回公共预热池，也不需要把所有有价值的中间状态都退回到最初镜像。

以并行修复为例，可以维护一个共同的项目准备基线，每条修复分支在其中独立修改；某条分支值得继续时保存它自己的进度，其他失败分支直接回收。最终保留补丁和证据，是否保留完整环境则由后续调试需求决定。这条流程使用了前面几种机制，但每一步都由明确的状态继承关系驱动。

本章的关键并不是“销毁比复用安全”这样过宽的判断，而是复用对象需要被精确选择。gvisord 让我们看到，一套系统可以反复使用准备好的检查点，同时丢弃每次执行后的内核状态。它并没有拒绝复用，而是在可信公共准备与任务私有变化之间划了一条能够落实到运行时的边界。

有了这条边界，下一章就能继续讨论真正的交付问题：一份状态即使可以恢复，一个环境即使最终可以回收，也仍需要在正确时刻被唯一地交给正确任务。恢复、领取和可访问，不是同一个完成事件。

五、能快速恢复，为什么还需要预热池和编排？

快照不会自行变成可使用的实例

前面已经解决了几项重要问题：公共准备可以保存，独立任务可以共享未变化内容，非活跃环境可以只保留状态，任务结束后也可以从可信基线重建。但调用者真正想得到的不是一份内存文件，而是一个现在能够执行命令、读取文件并接收后续请求的环境。

从制品到这个环境，中间仍然需要工作。系统要选择有资源的节点，准备运行对象、设备和网络，把正确版本的数据接入，等待必要的就绪条件，再建立调用者与实例的关系。底层恢复即使已经很短，也没有替这些动作决定顺序、归属和失败后的处理。

这就是本章进入另外四个层次的原因。池管理尚未分配的供应，租约表达一段独占使用关系，绑定使后续请求找到正确实例，编排持续协调期望与实际状态。它们不替代前面的状态机制，而是让这些机制能够以可使用的服务形式被交付。

可以把问题问得非常具体：请求 A 和 B 同时看到一个 ready 实例时，谁有权领取？实例创建完成但网络尚未就绪时，能否返回给调用者？某个实例被取走以后，谁补回库存？调用者几分钟后发来第二次操作时，又怎样知道它应该到哪台机器？这些都不是保存一份快照能够独立回答的事情。

预热到底提前完成了什么

预热池最基本的作用，是在请求到来前完成一部分准备。池里可以保存已经恢复并运行的实例，也可以只保存某些通用资源，例如已经准备好的网络槽位或运行时进程。不同池化对象对应不同的提前工作，不能都当作同一种“热沙箱”。

AgentENV 的公开架构包含网络、Firecracker 进程与块设备相关的预热机制。某些预热项把网络槽位和预先启动的 Firecracker 进程一起转给恢复中的沙箱，另一些则与块设备准备有关。这说明存储中心的按需恢复设计，也可以在具体启动步骤上使用池化。S13

为什么不直接把所有环境都提前恢复完成？因为完整实例通常绑定了更具体的模板、规格和初始化状态，并持续占用更多资源。通用资源的池可供更广的请求使用，却只能省掉其中一部分准备。池化得越靠后，命中时剩余工作可能越少；池化得越靠前，可复用范围可能越广。这是准备深度与匹配范围之间的关系。

例如，一个尚未绑定具体模板的通用网络槽位，可以服务多个环境的创建；一个已经加载特定业务数据的实例，则只适合满足相应条件的任务。前者不能让任务立即开始计算，后者也不能无条件替代任意请求。池里放什么，应当由值得提前做的工作以及它的适用范围共同决定。

因此，不能简单断言运行中的预热实例都是空壳，快照模板才是真正准备好的环境。一个运行实例可以从充分初始化的模板恢复，也可以完成额外的公共准备；一份内存快照也可能只保存到管理服务刚启动。准备是否有价值，仍然取决于第一章讨论的捕获点和就绪语义。

Daytona 把实例组织成一项平台服务

Daytona 的公开版本可以帮助观察，当底层环境被做成应用平台时，会增加哪些职责。它的 API 管理身份、元数据、生命周期和资源分配，Runner 在计算节点执行创建、启动、停止等操作，Proxy 把对沙箱的访问转到相应节点和服务。快照构建与保存则沿着该版本的镜像和 OCI 制品路径组织。S22

这里的分离首先是为了对应不同状态。API 需要知道一个实例属于哪个组织、期望处于什么状态；Runner 知道节点上实际发生了什么；Proxy 需要将某次访问送到当前承载实例的位置。它们围绕同一个沙箱协作，但保存的不是同一种信息。

例如，数据库里已经有一条创建记录，并不表示节点上已经完成启动；Runner 已经生成运行对象，也不表示外部访问路径已经建立。若把这些事件全部压缩成一个“创建成功”，调用者就无法判断自己得到的究竟是申请记录，还是可以立即使用的执行环境。

Daytona 的预热池把一部分实例提前创建并运行，在请求到来时寻找适配候选。其公开实现按快照、区域、资源规格、操作系统用户和环境变量等条件进行匹配，同时考虑运行节点是否适合被选用。这里的操作系统用户是执行配置，不应与发起请求的最终用户或组织身份混为一谈。S23

这些条件决定候选实例是否已经完成了请求需要的准备。区域不同可能意味着不能按要求交付；规格不同可能改变资源约束；环境变量若已参与初始化，领取后仅修改一个字段未必能恢复正确的业务状态。因此，匹配不是纯粹的查询优化，也是在维护准备结果与请求期待之间的一致性。

从找到候选，到唯一地交给任务

查到候选实例只是领取的第一步。考虑两个并发请求都从数据库读到同一个未分配实例：如果查询与归属变化之间没有协调，双方都可能以为自己拿到了它。即使运行时隔离本身没有问题，上层交付也已经破坏了任务独立性。

Daytona 的预热池实现在候选选择后尝试取得对应锁，再把候选交给后续流程；归属变更及相关事件又与库存补充相连。这些动作的设计目的，是使同一个现成环境不被重复交付，并使已经领取的对象退出原来的供应集合。S23

这里不能仅凭看到一把锁，就宣称所有并发与故障情况都已得到形式化保证。锁的生命周期、归属提交及重试方式仍然属于完整实现。但从机制角度，我们已经能够说明为什么纯粹的“查询一个空闲对象”不够：领取是一个改变使用权的状态转换，而不是只读查询。

一个通用的领取协议至少需要表达这样的关系：候选在被确认适配后，由无人占用转为某个明确调用者占用；其他领取者看到变化后不能再次得到同一个使用权。若调用超时或中断，后续恢复过程也应能判断归属是否已经完成，而不是盲目再分配一个对象。具体实现可以采用不同并发控制方式，本文不把示意协议当作某个项目的完整代码。

还要区分分配身份与访问授权。知道某个实例的地址，不等于被允许操作它；持有已经失效的地址，也不意味着继续拥有使用权。因此，把访问路径做得更直接，仍然需要维持组织、实例和占用关系的检查，不能把绕过这些判断当作池化优化。

绑定使后续操作回到同一项工作

领取成功以后，调用者往往还要连续操作。它可能先上传文件，再执行程序，最后读取结果。如果每次操作重新随机选择一个空闲环境，后续请求看不到前一次写入，任务就无法持续。平台需要把这段工作与具体实例连接起来。

Daytona 的代理根据沙箱标识与端口解析目标 Runner 并转发请求。API 层持有生命周期和组织信息，数据访问则通过对应路由到达实例中的服务。这个例子说明，创建时选择在哪里运行，与运行后每次访问怎样找到它，是相关但不同的问题。S22

绑定也不能仅理解为缓存一条永久地址。实例停止、销毁或在某种恢复流程中重新建立后，实际位置和可用状态可能变化。对调用者来说，逻辑上继续操作的是哪项工作，对平台来说则需要知道当前哪个运行对象能够承接它。二者之间的关系需要随生命周期更新。

这并不要求所有系统都进行跨节点迁移，也不意味着所有产品保留同样的沙箱身份。它只是说明，只要对外提供稳定的逻辑访问方式，就必须处理逻辑标识与实际执行位置的对应。底层快照提供可恢复状态，绑定提供找到当前执行的办法，两者不能互相替代。

在这个层次上，控制面与数据访问分离也有了直观意义。创建、暂停和归属变更是对生命周期的操作；发送文件、读取日志或与服务交互则是使用已经存在的实例。让每种请求进入适当路径，可以避免把所有活动都组织成重复创建，但并不会取消相应的身份与状态约束。

沿一份领取请求观察交付条件

把上面的关系放进一次教学请求。调用者希望取得一个使用模板 T、位于区域 R、满足某组资源配置的实例，并在其中继续多轮工作。这里不使用任何厂商的实际请求格式，因为重点是请求携带的约束怎样变成真实环境。

首先需要确定调用者是否可以使用这份模板，以及请求中的区域、资源和执行配置代表什么。只有经过这些判断，系统才知道哪些候选可以被交付。一个物理上存在的沙箱，如果不属于允许使用的资源范围，就不能因为它恰好空闲而交给请求。这是使用权的一部分，不是底层启动之后可忽略的附加步骤。

接着查找匹配的 ready 库存。若候选存在，需要协调归属，确认它没有被另一申请先取得；若没有现货，则按照平台策略创建、等待或拒绝，而不是把不匹配实例算作命中。候选在被锁定或登记为领取中以后，也还要完成明确的归属提交，才能由后续访问使用。

然后建立调用者能够使用的逻辑标识与访问关系。这个标识应当指向实际执行对象，而不是只指向某个模板版本。模板 T 可以生成许多实例，它们的状态来源相同，但后续请求必须回到本次领取的那个实例。否则上传与执行可能落到不同分支，任务会在没有明显启动错误的情况下失去连续性。

最后确认交付所承诺的就绪条件。若 API 只承诺异步创建已接受，就应返回可观察的创建状态；若承诺现在可以执行任务，则必要的运行与访问条件应当已经成立。两种协议都可以成立，问题在于不能让调用者把一种承诺误读成另一种。第一章的应用就绪，到这里成为对外接口语义的一部分。

假设响应在返回途中丢失，调用者并不知道领取是否已经完成。具有可观察申请对象的系统，可以让它查询已有状态，再决定是否继续等待；若每次超时都重新发起完全无关联的领取，就可能产生额外实例。这个场景说明持久申请与重试关联为什么有用，但不代表拥有一个 Claim 对象就自动得到所有端到端去重保证。S25S26

库存被取走以后，谁来补充

预热池不是一次性准备一批对象就结束。实例被领取以后，原来的未分配库存减少；创建失败或节点不可用也会改变供应。系统若希望继续维持某个目标数量，就要持续观察差距并补充。

Daytona 的公开实现既包含由归属变化触发的补充逻辑，也包含周期性检查。事件使系统能够及时响应已经发生的领取，周期性检查则根据当前状态重新判断库存是否不足。这两条路径围绕同一个目标工作：实际供应变化以后，不依赖调用者自己记得补回一台机器。S23

这里还有一个重要细节：用于补充决策的数量，与能够立即领取的数量可能不同。一个新实例已经开始创建，却还没有 ready；它应当在防止重复补充时被适当考虑，但不能因此被当作现货交付。前者关注有多少供应正在形成，后者关注现在可以交付多少。

如果忽略在途创建，控制器可能每次检查都看到 ready 不足，于是不断重复发起创建。如果把所有在途对象都视为 ready，调用者又可能被交付尚未准备完成的环境。两种计数承担不同职责，不能为了少维护一个状态而合并。

第四章的 draining 也是相同逻辑。它已经不属于正在执行业务的集合，却还没有回到可供应集合。池管理需要理解这些中间阶段，才能把资源实际存在、正在准备、正在使用和可以领取区分开。只列出一个总实例数，无法表达当前交付能力。

事件通知与周期对账各自补上什么

事件驱动听起来比周期检查更及时，但二者处理的并不是完全相同的问题。一个领取事件告诉系统“刚刚发生了值得重新判断库存的变化”，实际库存则由当前对象状态决定。若只根据累计事件数维护一个计数，重复通知、处理失败或重启就可能使计数偏离实际情况。

周期对账提供另一种依据：重新读取当前对象，比较它们与目标状态之间的差距。即使某次事件没有及时完成处理，后续对账仍有机会发现缺口。Daytona 的事件补充和周期检查体现了这两种触发方式；Kubernetes 控制器则把持续比较期望与实际作为基本工作模式。S23S27

用一个简化例子说明。池目标是十个未分配环境，两个实例刚被领取，补充已经发起但尚未 ready。若下一次循环只看 ready 为八，就再创建两个，可能导致四个在途对象；若能同时看到前一轮已经存在的创建意图，就可以避免把同一缺口重复扩大。等创建失败，再根据新的实际状态判断是否重新补充。

这要求对象与状态表达足够明确，而不只是把一个整数加减得很快。处于创建中的对象、已经被领取的对象和可以领取的对象，应当能够按各自含义被识别。不同实现可以有不同数据模型，但控制循环需要的事实不能仅存在于上一次函数调用的局部变量中。

并发控制也应当围绕实际状态转换。两个控制循环同时发现缺口时，不能都无条件把自己的旧判断写回；领取时也不能用过期读取覆盖已有归属。Kubernetes agent-sandbox 的 Claim 控制器使用乐观更新及归属核对，就是在处理“读完之后状态可能已经变化”的具体问题。S26

这些机制让重试有了意义：重试是再次读取并根据当前状态推进，而不是机械重复上一次的副作用。控制器的价值也因此不只是后台跑一个定时任务，而是把未完成工作表示成能够重新观察、继续协调的关系。它仍需正确实现，但其设计动机可以从这些中断与并发条件直接推出来。

Kubernetes 为什么把这些关系做成资源对象

Kubernetes agent-sandbox 采用更显式的资源模型。SandboxTemplate 描述可复用配置，SandboxWarmPool 表达需要维护的预热供应，SandboxClaim 表达领取请求，而 Sandbox 承载具体环境。控制器负责根据这些对象协调实际运行。S24S25

这个设计首先改变了调用者要维护的内容。调用者不必直接遍历所有 Pod，找一个合适对象、修改归属，再自行补充。它可以提交一份明确申请，让系统去完成相应关系。申请对象本身可以被观察，实际环境变化以后也有相应记录可以核对。

为什么不只提供一个立即创建的函数？在分布式系统中，调用发出之后，创建可能还在进行，调用者可能超时，控制器也可能重新启动。如果意图只存在于一次函数调用的栈里，恢复以后就难以判断还有什么工作没完成。把期望保存在资源对象中，控制器可以再次比较期望与实际，继续推进尚未完成的动作。S27

这不是说声明式模型自动消除了所有错误。控制器仍需要正确处理并发更新、对象归属、删除与重试。agent-sandbox 的 Claim 控制器包含归属验证、乐观并发控制和冲突重试等逻辑，说明一份申请如何绑定到具体实例，仍然需要落实到真实状态转换。S26

例如，控制器读到某个候选时，它可能还没有被其他 Claim 占有；提交变更前，另一个控制器循环可能已经改变了归属。带版本的更新可以使这种冲突变得可检测，控制器再根据新的实际状态判断，而不是用旧的读取结果覆盖别人的领取。这里介绍的是这种机制为什么需要存在，不是对完整控制器作代码审计。

编排对象不能替底层实现隔离和快照

资源模型清楚以后，还要避免另一种跨层推断：因为有 Sandbox 和 WarmPool，就认为平台已经具备某种特定微虚拟机及内存克隆能力。Kubernetes agent-sandbox 的公开范围说明，它是沙箱编排器，通过 Pod 与 RuntimeClass 等配置把底层隔离交给相应运行时。S24

这使它能够在编排层统一某些生命周期和申请方式，却不意味着所有底层拥有相同的状态保存能力。gVisor 与 Kata 等运行时的实现不同，某项内存恢复或克隆能力需要具体运行时及集成路径支持。不能把一个声明式资源当作实现任意底层机制的承诺。

从前面几章看，这个边界其实很自然。快照文件由什么组成、内存怎样恢复、写入怎样私有化，属于制品与实例的运行机制；Claim 如何唯一领取、库存如何补充，属于使用权和编排。两者可以配合，却不会因为共享一个 API 名称就自动互相补齐。

这也意味着，一个已经具备快速恢复的运行时，仍可能需要与现有编排系统结合；一个成熟的编排器，也可以根据工作负载选择不同底座。多系统比较时应当先说明谁承担哪层，再讨论同层机制的代价，而不是把这些项目看作必须完整替换彼此的单体产品。

配置差异为什么会变成库存碎片

现在考虑池里有足够多实例，却仍然不能满足请求的情况。假设有十个用于纯 Python 分析的实例，以及十个加载了特定浏览器配置的实例。突然来了十五个浏览器任务。库存总数是二十，但适配的现货只有十个。

这个例子是教学假设，不是某个厂商的限制。它说明库存是否足够，应当按可替换关系判断。不能把所有 ready 对象加起来，就当作任意请求都能消费的统一资源。快照、区域、规格或初始化配置越具体，可能形成的适配类别就越多。

Daytona 的匹配字段让这种关系变得可见。一个实例已经以某个操作系统用户和环境变量启动，它的进程状态可能依赖这些条件。若另一个请求期待不同环境，直接放宽匹配并不一定得到正确实例。命中率提高了，可能只是把不适配的对象也算作成功交付。S23

一种通用的分析方法是回到初始化过程，检查哪些差异必须在公共准备之前确定，哪些可以在独立领取之后再提供。对于后者，可以减少提前固化的配置范围；对于前者，则需要接受它们形成不同库存类别，或者改变应用初始化方式。这个判断需要真实的状态依赖，不能只根据字段名称决定。

比如业务筛选条件若只是服务请求的参数，就可以在领取之后传入；若同一个字符串决定启动时加载哪份数据，并已经产生不同内存对象，它就影响基线。二者都可能写在 JSON 中，却不能因为传输形式相同就被视为同一种晚绑定配置。

因此，预热池设计并不是单纯把目标数量加大。还需要理解每一类库存覆盖什么请求，以及提前准备的结果为什么能够在这些请求之间共享。第一章的公共基线选择，在这里直接变成了供应的可替换范围。

池深与补充吞吐不能用同一个数字表示

一个池预先有多少实例，决定它能立即承接多少匹配请求。补充吞吐则决定取走之后能以什么速度形成新库存。两者相关，但不是同一个参数。特别是，不能普遍把补充 QPS 写成“池大小除以平均创建时间”，除非另有前提证明池大小恰好决定了有效创建并行度。

用一个简化模型说明。假设创建过程始终允许 C 个操作并行，每个操作平均占用创建位置 T 秒，而且没有其他限速或瓶颈，那么稳定形成实例的速度大约是 C / T。这里的 C 是有效在途创建并行度，不是池中已经准备好的库存数量。

若池深是二十，创建并行度是四，每次创建平均两秒，按这个模型补充速度约为每秒两个。把池深改为四十，可以增加预先保存的现货，却不会仅凭这一改动把同样四个创建位置变成每秒二十个。若同时改变了并行度，那是另一个动作，应当分别描述。

实际系统还可能受 API 限速、镜像读取、节点资源或其他环节约束，所以 C / T 只是解释并行工作与平均吞吐关系的模型，不是容量保证。创建时间也可能随并发变化，不能用低并发下的 T 推导任意并发下的供应速度。

再看一个连续流量的教学近似：假设当前库存二十，匹配请求平均每秒取走五个，新实例平均每秒形成两个，并暂时忽略离散完成和其他波动，那么库存平均每秒减少三个。扩大初始库存可以延后耗尽时刻，却不能改变长期入少于出的关系。池是缓冲，不是凭空增加持续产能。

这个推导也解释了为什么要关心补充提前期。一次突发取走库存以后，新实例不会在发起创建的瞬间出现。在这段间隔内，仍需要现有库存或等待策略承接请求。平均供应足够与每个瞬间都不缺货，是两个不同条件，不能把平均 QPS 当作全部延迟分布的证明。

补充本身也可能和任务争用资源

提前准备不是没有成本的后台动作。恢复模板要读取数据，启动实例要使用 CPU 和内存，创建网络与设备也需要系统工作。如果库存下降后一次性发起大量补充，这些准备可能与正在执行的任务竞争相同资源。

因此，补充控制除了目标数量，还需要理解工作如何进入系统。批量规模、有效并发以及在途数量会影响准备过程的集中程度。某些实现提供显式限速或批处理参数，另一些需要由外围系统约束；不能因为存在 WarmPool 对象，就推断所有项目都有相同的补充节奏控制。

从机制上看，立即把缺口全部转为创建请求，可以较快表达补货意图，却不保证最早完成所有实例。如果下游过载导致单次创建变慢，甚至影响现有任务，就可能需要更受控地形成供应。是否存在这种问题，要通过具体路径与负载观察，而不是预设某个固定批量一定最优。

这里也不要把库存不足简单归为底层沙箱启动慢。可能是匹配类别不对，可能是创建被限速，可能是回收尚未完成，也可能是路由和归属还没提交。只有知道等待发生在哪个层次，才知道应该改变模板、运行时、池策略还是控制流程。

三种不同的“热”，为什么会被混成一个数字

讨论启动时，经常把制品已缓存、实例已恢复和应用已就绪都叫作热环境。但三者省去的工作不同。制品在本地，只意味着少一段数据获取；运行实例存在，意味着一些运行时准备已完成；应用达到就绪条件，才说明相应业务初始化已结束。一个层次热，不足以推导其他层次也热。

例如，同一台机器上的模板文件已经缓存，但仍需建立虚拟机与服务；另一个池中有现成虚拟机，却还没有加载特定任务的数据。两者都可能减少请求等待，但剩余路径不同。若将它们都称作 warm hit，再直接比较返回数字，就会忽略被测操作究竟完成到哪里。S01S05S13

可以沿任务开始所需条件来区分：数据是否已在可读取位置，运行对象是否已建立，应用公共准备是否已结束，归属和访问是否已确认。每提前满足一个条件，都要有相应资源或制品支撑。预热不是一个二值开关，而是若干准备动作已经完成的组合。

这样也能解释某些表面矛盾。一套系统的创建返回较早，可能因为后续数据按需读取；另一套系统返回较晚，可能已经完成更深的准备；现成池命中很快，又可能在持续流量下等待补充。这些现象需要沿不同完成点解释，不能仅凭单一接口名判断整体任务开始得更早。

对外承诺是什么，就应当按相应条件观察。若关心任务第一步能否开始，就不能只记录请求已被接受；若关心持续供应，也不能只观察库存充足时的第一次领取。指标应跟随已讲清的过程，而不是替代过程。

看懂“已经交付”需要哪些条件

现在可以回到调用者最直接的问题：什么时候我真的得到一个可用沙箱？一个合理的回答需要同时对应任务要求、独立归属和可执行状态。只存在制品不够，只发起创建不够，只看到进程不够，甚至仅有一个稳定标识也不够。

在具体系统中，这些条件可以通过不同协议组织，但含义不应混淆。实例应当符合请求的环境条件，当前使用权应当明确，必要的服务应当就绪，访问应该路由到正确执行对象。之后的回收也应当终止旧使用权，而不是让旧客户端继续把曾经有效的地址当作永久权限。

这不是要求所有平台采用同一个复杂状态机。若任务简单、调用者可信且只在单机使用，可以采用较轻的组织方式；若需要多租户、多节点和大量并发，就有更多状态需要明确。设计复杂度应来自实际交付关系，而不是为了与别家拥有相同数量的组件。

至此，前面几章的机制终于接成完整工作：制品保存公共准备，运行时恢复独立实例，CoW 延后不必要复制，存储保存需要延续的变化，回收丢弃不应继承的现场，池把部分准备提前，租约和绑定把实例交给正确任务，编排在实际环境变化时继续维护这些关系。

这些层次之间可以有很多组合，并不存在一个项目只要拥有其中最深的快照机制，就自动覆盖其余全部职责。理解开源设计的价值，正在于能够沿着具体工作找到相应层次，再判断它怎样满足约束、承担什么代价，以及什么前提改变后需要重新选择。

结语：独立运行，不必从零开始

回到文章开头的一百个 Agent。现在我们可以不依赖某个产品名称，描述它们需要的系统行为。首先准备一份内容与条件明确的公共起点，让它包含真正值得反复使用的工作结果；随后为每项任务建立独立运行，使未变化的内容仍可共享，而变化只进入各自的状态；任务等待时，根据需要保存现场并释放执行资源；任务结束时，保留有价值的结果，丢弃不应流向下一项工作的私有变化。

这条过程的难点，不只在于任何一个动作能否执行。准备的结束点必须与恢复后使用的入口一致，共享的数据必须是能够保持确定含义的版本，保存范围必须足以支持所承诺的恢复，回收范围又必须覆盖所承诺丢弃的状态。最后，实例还要在正确时刻交给正确任务。任何一条对应关系缺失，局部机制即使很快，也可能无法兑现整体体验。

复用的价值，要沿着工作量变化判断

文章中出现了几种不同的节省。有些把已经做过的计算保存下来，下次不再执行；有些不再为相同内容立即复制全部字节；有些只读取任务实际访问的部分；还有些把准备提前完成，让用户请求到来时少等待。这些变化可以同时出现，但不能不加区分地合成一句“启动更快”。

尤其是提前工作，与减少工作并不相同。预热池里的实例如果最终没有被任何任务使用，提前准备仍然消耗过资源；按需读取如果后来访问了全部内容，也没有因此免除全部读取；写时复制如果最后产生了大量分歧，就要承担相应私有内容。设计的价值，需要结合工作是否真的被复用以及什么时候支付成本来判断。

这并不是说某种机制不值得采用，而是让收益有具体前提。很多请求共享稳定的初始化，保存运行态就有明确对象；大量实例主要读取共同基线，CoW 就有持续可共享的内容；长时间等待又需要延续现场，保存状态与执行资源分离就有意义。条件变化以后，也应允许选择变化，而不是为了延续一个产品标签坚持原办法。

共享越深入，越需要明确版本与边界

复用文件时，文件版本决定任务得到哪些代码和依赖；复用运行态时，捕获时刻、初始化条件和机器兼容性也进入制品含义；复用共同层时，哪些状态仍然引用它们又影响数据生命周期。共享减少了重复，却增加了对来源关系的依赖。

因此，版本与归属并不是与性能无关的外围管理。一个模板不能说明自己是什么，就无法可靠判断请求是否适配；一个快照不能确定它依赖哪些内容，就无法保证删除与恢复正确；一个实例没有明确占用关系，就可能把任务本应独立的修改交给另一个调用者。高效复用始终以清楚的对应关系为前提。

这也解释了为什么只复用较浅层状态，有时是合理选择。若应用容易重建、运行条件多变或公共部分很少，保存更深状态可能带来额外兼容与管理成本。反过来，如果初始化昂贵且长期稳定，反复从文件启动也会持续支付可以避免的工作。深度不是一条单向的优劣刻度，而是与工作负载条件相匹配的范围。

项目之间的差别，需要在同一层比较

看完这些实现，再把它们摆进一张“谁支持快照、谁支持池”的表，会发现很多单元格需要补充语义。快照可能指文件内容，也可能指整个运行状态；CoW 可能发生在存储区段，也可能发生在运行内存页面；池可能持有完整实例，也可能只预先准备网络或进程。相同功能名不保证同一种机制。

另一些项目的差别来自职责范围。一个运行时专注于保存与恢复，另一个平台还要管理组织、路由和生命周期，一个 Kubernetes 扩展则把申请和库存表达成声明式资源。没有实现某个上层职责，不必然说明底层能力较弱；具备完整控制面，也不能替代对底层恢复路径的核实。S01S13S22S24

因此，对 Daytona 之类平台，更具体的问题是它的公开版本把哪些准备固化为制品、池里提前运行了什么、领取与路由怎样组织，而不是仅凭产品出身判断它只能服务某种任务。对 forkd、CubeSandbox 或 AgentENV，也应当先确认所需的是状态派生、存储共享还是持续供应，再看它们对应层次的行为。本文不从一个原语推出整个产品必然适合所有 Agent 场景。

接口兼容同样需要沿语义理解。两套系统都能接收一个类似的创建请求，并不自动意味着它们对就绪、暂停、身份、存储和回收作出完全相同承诺。真正可替换的范围，取决于上层任务依赖哪些行为。客户端能够发出请求，只是这些行为能够被使用的入口，而不是全部行为相同的证明。

环境生命周期应当服从任务生命周期

对于独立的短任务，重点可能是从可信基线取得环境，并在结果收集后完整丢弃私有状态。对于需要长时间继续的会话，重点可能是保存有价值的现场，把空闲时间从持续执行占用中分离。对于并行分支探索，重点则是找到共同进度，并让后续分歧以独立状态发生。

这三种工作甚至可以在同一平台内出现。一个 Agent 先在长会话中理解项目，再从某个进度派生若干短分支，最后把选中的结果带回后续工作。系统不必选一个永久的“有状态”标签，而需要在每个边界清楚表达：哪里应当延续，哪里应当分支，哪里应当回到基线。

当这些边界清楚以后，底层机制才有明确用途。快照负责保存需要延续的状态，写时复制负责延后不必要的分离，分层存储负责表达共享基础与变化，重建负责丢弃不应继承的运行现场。池、租约、绑定和编排则把这些能力组织成能够被任务持续使用的供应过程。

最终，开源 Agent 沙箱设计带来的认识不是“独立环境一定很便宜”，而是独立运行不再必然意味着完整重做准备和完整复制一切。我们可以根据状态的共同部分、变化位置和使用时间，把工作安排在更合适的阶段。代价仍然存在，只是能够被拆开、理解，并围绕实际任务作出选择。

如果需要用一句话概括整篇文章，那就是：复用的是已经完成且允许继承的工作，隔离的是各项任务之后产生的变化，调度的是这些状态什么时候需要成为真正运行的实例。 把三者分开设计，再在明确边界上连接起来，才是这些开源实现背后值得学习的共同思路。
