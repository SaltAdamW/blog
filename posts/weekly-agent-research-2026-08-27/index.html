本期选读模型架构、长任务、安全调查与记忆更新，并补入 Factory 的完成标准设计和 Prime Agent 的持久运行机制。文末另附三篇待精读原文。

Qwen：低激活参数之外，还要处理长上下文和模型容量

原文：Qwen3.8-Flash-Next 官方仓库与架构说明 · 2026-08-26

模型每次只激活少量参数，并不意味着长上下文就便宜了。历史信息仍要被保存和访问，模型的总容量也仍然需要存储。Qwen 这次开放的架构预览，分别处理了这些成本。

其中一部分历史交给 Gated DeltaNet 压缩；需要从长上下文中找回的信息，则由稀疏注意力 QSA 的轻量索引器挑选相关小块，再参与注意力计算。这样，压缩历史和访问历史由不同机制承担，避免把每一段历史都按同样方式反复处理。

另一项改动是 N-gram Embedding。它依据局部上下文查表，为模型补充容量，表可以放在主机内存中，通过异步预取与模型计算重叠。官方给出的规模是 1250 亿主模型参数、额外 510 亿查表参数，每个 token 激活约 60 亿参数。这个区分很重要：60 亿描述的是每步参与计算的量，不能据此把它当成只需存储 60 亿参数的小模型。

这次发布还同时修改了残差连接和优化方法，属于一套架构组合的预览。值得读的是它怎样分配计算、容量和历史信息访问的职责；整体模型的成绩不能直接说明其中某个组件单独贡献了多少。对于部署，低激活量之外，主机内存、数据搬运和具体推理实现仍是需要核对的条件。

NVIDIA AVO：一次持续七天的内核优化怎样保留进展

原文：NVIDIA AVO 的长任务架构与 ARC-AGI-3 实验 · 2026-08-21

优化 GPU 内核时，改动看起来合理，不代表运行后更快。编译、正确性测试和性能分析都可能推翻原来的设想。任务持续几天之后，Agent 还得记住哪些方向试过、为什么放弃，以及当前最好的实现是什么，否则大量时间会花在重做旧实验上。

NVIDIA 的 AVO 把这些实验状态留在持久记忆中，包括代码版本、评测结果、编译器和性能分析器输出，以及此前的判断。主 Agent 决定下一步检查、修改和测试什么；另一个监督角色观察较长一段搜索过程，在停滞或反复走无效路线时提出调整。这里需要保存的是可继续使用的实验记录，而不只是上一轮对话的摘要。

作者报告，在一次连续七天的注意力内核优化中，系统探索了五百多个方向，提交了四十个内核版本。这个案例展示了长时间迭代的过程，但七天运行本身并不是成本优势的证明，也没有单独分离记忆和监督各自带来的收益。

团队又把同一套基本架构接到 ARC-AGI-3 的交互环境。在公开集的 25 个环境、183 个关卡上，完整系统取得了 100.00 的 RHAE 分数。这里必须保留“公开集”这个范围，不能写成私有竞赛集成绩，更不能从不同运行配置的模型分数反推出某个组件的贡献。

这篇文章适合关心长任务执行的人读：它给出了“模型换一轮上下文后，实验怎样接着做”的具体设计，也留下了一个待验证问题，即这些额外记录和监督，在自己的任务中能减少多少重复探索。

微软安全调查：网关被攻破，损失可能不止一把模型密钥

原文：When AI infrastructure becomes the target · 2026-08-26

统一网关让应用不必各自管理模型连接，却也把供应商密钥、数据库连接和租户配置集中到了同一个服务附近。微软本周公布的三起调查涉及 LiteLLM、RAGFlow 和 Kestra，展示了攻击者拿到这些服务的执行权限后，还能接触什么。

在 LiteLLM 案例中，攻击活动从网关进程出发，读取运行时凭据，再访问后台数据库中的模型配置和代理密钥。RAGFlow 案例的做法不同：攻击者修改了应用加载路径，在用户新增或调整模型配置时截获凭据。后者意味着，仅更换一把旧密钥可能不够，尚未清除的应用篡改仍可能拿到新密钥。

Kestra 案例则暴露了运行环境边界。工作流执行后，攻击者通过可访问的 Docker socket 枚举其他容器及其环境信息。容器中的任务能否接触容器运行时，决定了影响会不会越过当前工作流。把服务装进容器，不自动等于它只能访问自己的数据。

这些都是入侵后的观察记录，不应写成三个产品共享同一种漏洞。微软尤其没有确定 RAGFlow 案例的具体入口漏洞。对防守方，更可操作的检查是：管理面是否暴露、服务进程能读哪些秘密、能启动什么子进程、能连接哪些外部地址，以及应用文件是否被修改。只盯着提示注入，会漏掉这类传统入侵路径在 AI 系统中的后果。

OpenWiki：代码变了，旧知识怎样重新变得不可信

原文：Building Self-Correcting Memory in OpenWiki · 2026-08-25

一份代码 Wiki 写着“任务失败后默认重试三次”，最初有实现依据。几次提交之后，相关代码发生变化，这句话却仍可能被检索出来，继续影响 Agent 的判断。能够找回旧知识，并不能回答它现在是否还成立。

OpenWiki 在写页面时，同时记录其中的事实声明、支持它的代码位置和证据版本。每次更新开始，运行时先比较保存的证据版本与当前版本。如果不一致，就把相关声明作为待复核内容交给 Agent。代码变动只是重新检查的理由，不等于声明已经错误。

复核有两种结果：声明仍然成立，就刷新证据版本；声明已经不成立，就一起更新页面和证据。没有处理完的声明不会因这一轮结束而被默认恢复可信。保存的版本差异让下一轮仍能发现它需要检查，不必依赖模型记住一条待办。

这种更新不要求每次重写整份 Wiki。确定性检查会扫描声明集，而模型在读取相关页面时处理其中的过期声明。作者还用连续代码提交回放新增功能、行为变化、修复和回退，检查 Wiki 能否跟上。它提供的是一种维护知识的办法：让“为什么相信这句话”与正文一起保存，同时承认未完成的复核仍是未完成。

Factory：代码写了很多，谁来决定任务已经完成

原文：What It Takes for Coding Agents to Complete Large Software Tasks · 2026-08-27

大型软件任务常常停在一个很像成品的中间状态：主要路径能运行，部分功能仍是空实现，Agent 却已经开始写交付说明。Factory 在 ProgramBench 任务中观察到，单 Agent 会逐渐缩小自己认定的完成范围。继续增加执行时间，不一定能纠正这个停止条件。

他们先让验证角色把任务要求转成可执行的完成标准，再由编排者、实现者和验证者反复推进。实现者接收缺陷分类与待完成范围，不直接看到验证用例；验证者独立运行检查，把未覆盖的功能送回下一轮。这样，尚未实现的部分不会因为实现者已经写出一段自洽的总结就消失。

实验选取了 24 个较难的任务，对比多种模型在单 Agent 和完整系统中的表现。结果支持继续研究这种组织方式，但不能读成等费用下的普遍提升：两种条件没有匹配计算预算，每个配置只有一次运行，部分运行还更换了模型。对自己的代码任务，更值得复用的是独立完成标准、缺陷反馈和停止判定，而不是直接套用图中的涨幅。

Prime Agent：上下文换了一轮，工作状态怎样留下来

原文：Prime Agent: A Self-Improving RLM Harness，arXiv v1 · 当前技术报告版本为 2026-08-24，首次公开于 2026-08-05

长任务里有两种容易混在一起的状态：模型这一轮看到的上下文，以及程序已经算出的对象、历史记录和工具定义。把全部工作都放在聊天记录里，压缩或重新开始会话时，就容易连同可继续使用的状态一起丢掉。

Prime Agent 把持久 IPython REPL 作为工作环境。历史、记忆、skills 和子 Agent 定义保存在上下文之外，由程序按需查询和加载；后台 daemon 维持会话，客户端断开不等于任务必须结束。模型面对的是当前需要处理的材料，完整工作记录则继续留在环境里。

标题中的“自改进”指对 harness 及其相关状态做版本化修改，模型权重并没有随之训练。恢复也有边界：不可序列化对象和外部进程，不能仅靠保存 Python 状态就保证原样续上。这份报告适合与 NVIDIA AVO 对照阅读，分别看运行状态和实验记录怎样跨越上下文窗口；整体评测分数仍不能单独归因于 REPL 或记忆组件。
