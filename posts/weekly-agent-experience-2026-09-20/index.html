这一期选六篇当周公开的原作者研究与复盘：查库后交不出答案、从历史轨迹学习却没能上线、浏览器操作受限、代码迁移漏掉接口、多 Agent 协作的等待成本，以及规划评测中的“通过”究竟意味着什么。部分工作发生在此前几个月，文中分别标明复盘日期与实验时期。

1. 数据库 Agent 写出了建议，为什么工具还说缺少内容？

9 月 18 日公开：What Stops a Small Language Model From Driving a Database Agent。真实 SQL 客户端中的测试，使用固定 SQLite 样例数据库。

LibreDB Studio 的用户中，有人不愿把数据库结构和查询发给外部模型服务。开发者于是测试本地模型，想知道它们能否完成查库、分析、提交报告等工作。研究记录了此前十一天的运行，覆盖五类可调用工具的任务，以及一类不调用工具的规划任务。

一次优化查询的调用暴露了具体问题：模型把建索引的 SQL 放在 change 里，把理由叫作 reason，把一条证据写成对象。工具要求的却是：change 填 index 或 rewrite，SQL 放在 statement，理由放在 rationale，证据必须是数组。内容已经生成，校验器仍判定缺少语句和理由。

开发者最初只能看到拒绝原因，看不到实际参数。补充临时参数捕获后，才分清“模型没有写出内容”和“内容写在了别处”。同类错位多次出现，重复返回缺字段消息，没有可靠地让模型自行改正。

服务端随后增加了有限的参数归一化：明确的别名转成规范字段，单个证据对象包装成数组，能够识别的 SQL 移到对应字段。这里需要保留边界：转换已有的值，不替模型补造理由；有多个可能对应关系时，也不能随意猜一个。

另一个问题发生在两个相邻工具之间。present_answer 需要 presentation，模型却把它交给 compose_report；后者只说“删除这个字段”。作者改成说明字段应交给哪个工具，因为这份展示信息仍然是完成任务所需的内容。公开捕获缺少运行编号和时间顺序，能够证明结构冲突，不能证明模型曾因这条反馈删除答案。

这类问题值得优先查，但不能把所有拒绝都当作格式问题。 我们复算作者的运行摘要和逐条拒绝记录，两份文件的计数一致：

观察范围 结果 能说明什么
有模型归属的工具型失败运行 1,590/2,100 次至少调用过工具，即 75.7% 多数失败不是完全没有行动，不代表行动正确
全部运行中的工具拒绝 14,008 次 一次运行可以多次被拒绝
报告工具的拒绝 9,707 次，占 69.3% 交付报告是值得检查的集中位置
报告工具拒绝的构成 输入不合法 6,243 次；证据不可核验 3,464 次 两类错误不能用同一种“放宽校验”处理

证据校验要求报告引用本次运行实际产生的查询结果或结构快照。把证据包装成数组，只能修好表示；其中的编号如果找不到真实结果，仍应拒绝。这也是参数兼容不能顺手取消事实核验的原因。

作者报告，整组服务端修改后，granite4.2:3b 从 21/30 次通过变成 28/30，llama3.1:8b 从 10/30 变成 24/30。每组是六类任务各五次，通过看最终 answered，不是进程正常退出。部分改前读数拼接了不同日期与设置下的结果，又存在选择低分任务重测的问题，所以差值不能当作单项修复的净收益。单独调整文本中工具调用的识别时，四个任务组合只得到增加 1 次、不变、不变、减少 1 次，没有清晰收益。

遇到同类失败，可先检查被拒绝参数里是否已有所需内容，再决定修接口、补信息还是更换模型。验收继续看报告和证据是否真正交付，不能只看错误消息少了多少。完整参数捕获

2. 用历史轨迹教 Agent 纠错，为什么学会了一部分仍不上线？

9 月 20 日公开：Fast Memory, Slow Weights。Scalably 的第一方报告，训练尝试发生在 8 月。

Scalably 的业务 Agent 已经留下大量工具调用、失败与恢复记录。团队希望把这些经验变成模型行为：工具出错后，不要机械地重复同一个失败动作。它从历史轨迹筛出两组各 423 条训练记录，训练两个 LoRA 适配器，再用训练前冻结的任务集合，与原始模型配对比较。

评测把“刚失败后怎样恢复”和“原本正常的任务会不会变坏”分开。424 个留出决策中，264 个是正例，包含 73 个恢复状态、73 个无故障轨迹状态和 118 个其他已验证动作；另外 160 个是历史失败动作发生前的状态。还有 60 个训练分布样例只作训练有效性检查，不混入留出结果。

这个分组很重要。只测恢复状态，可以看到模型有没有学到目标行为，却看不到相同权重改变对正常任务的影响。Q-only 组的结果恰好出现了这种分歧：

评测对象 原始模型 训练后 变化
恢复状态匹配正确 31/73 38/73 增加 7 个
重复历史失败动作 32/160 24/160 从 20% 降至 15%，相对减少 25%
正常轨迹匹配正确 49/73 45/73 下降约 5.48 个百分点
全部正例匹配正确 138/264 141/264 只增加约 1.14 个百分点

“匹配正确”的口径也比日常理解窄：工具名称正确，且参数键集合与历史记录一致。它不检查参数值，不是重新执行完整业务任务。本组正例中，工具选择本身没有变化，变化发生在参数键集合。

团队在训练前设定的准入规则包括：正常任务下降不超过 2 个百分点，总体正确率至少提高 5 个百分点。目标错误虽然减少，两条规则却没有满足，两个适配器最终都被拒绝，没有上线。

正常轨迹的下降是否说明遗忘？还不能确定。73 个样本中，3 个变好、7 个变差，配对检验的 p 值约为 0.34，尚不能排除噪声。这里的不上线，是执行预先设定的点估计准入规则；它不等于证明微调必然破坏旧能力。训练集未包含正常轨迹样例，也让后续验证有了明确方向：加入保持原行为的样例，再看目标收益能否保留。

团队另行采用了按工作空间保存的外部记忆。规则有稳定编号、来源和替代记录，可以单独撤销；写入权重的适配器则需要整体卸载，无法直接只保留这次纠错收益、删除那次正常任务下降。外部记忆的任务收益尚未测量，因此这份报告没有证明“记忆比训练更有效”。它提供的经验是：让历史经验进入共享权重前，同时检验目标行为、原有行为和总体结果；可局部撤销的经验，先保留可追溯的形式。

3. 浏览器 Agent 看不到按钮时，增加点击工具并不能解决问题

9 月 15 日复盘：The Bitter Lesson of Browser Agents。Browser Use 的工程演进；下述 Hermes 对照已于 8 月公开，不是本周新实验。

Browser Use 早期替模型定义两件事：页面是什么样，以及模型能做哪些动作。前者是一份经过处理的页面状态，后者是点击、输入、滚动等固定工具。这个设计方便控制，但网站上的特殊交互不断增加，开发者需要持续补动作和状态提取规则。

第一步调整是让模型写代码执行动作。循环读取评论、处理一组元素、画签名等操作，不必每种都新增专用工具。代码里的中间结果可以继续参与后续处理，也不必每做一个细小动作就把控制权交回模型。

但动作变灵活后，观察仍然可能有缺口：Cookie 按钮明明在屏幕上，却没有进入提供给模型的页面状态。它可能没出现在所用的无障碍信息中，也可能被预处理漏掉。模型无论怎样选择点击动作，都无法可靠操作一个没有被呈现给它的目标。

团队随后把观察也交给模型按需组织：通过 Chrome DevTools Protocol，写代码查询 DOM、检查某个 frame，或取截图。变化不在于取消浏览器状态，而在于不再要求所有网站先适配一份固定表示。当前问题是按钮在哪里，就取能回答这个问题的观察；当前问题是多页数据怎样汇总，就尽量在代码里处理已获得的数据。

Hermes 的一次接入对照提供了有限的实测参照：六类多步任务，各跑三次；在同一模型下比较原来的十二个浏览器工具与 browser_exec。开发者使用不同 worktree 固定两组代码，并移除网页直取工具，要求两组都通过浏览器完成任务。

模型 原工具组平均 token 代码工具平均 token 两组完成情况
opus-4.8 64,594 25,934 均为 18/18
kimi-k3 56,464 19,230 均为 18/18

按表中数字计算，减少约 59.9% 和 65.9%。但这些是 toscrape 一类测试站点上的结果，每个任务只有三次，没有重型单页应用或反爬挑战。另一个较容易的测试组中，Qwen 模型的收益不明显，作者观察到它在重试执行代码时消耗了节省下来的 token。原始接入 PR 与评测口径

代码工具也改变了权限边界。该接入允许执行宿主机 Python，因此对没有终端权限的会话，直接从工具定义中移除 browser_exec；不支持 CDP 的浏览器则回退原工具组。工具数量减少，不意味着权限更小，也不意味着每个模型都能用好新的接口。

这条经验适合区分两类症状：模型知道目标但动作表达受限，可以考察代码化执行；模型压根没有获得目标信息，就先检查观察链路。原文的对照支持特定代码工具接入的 token 变化，没有单独证明“放开观察选择”贡献了多少收益。

4. Agent 把迁移检查变绿了，但接口被删掉了

9 月 16 日复盘：Migrating the GitHub Copilot runtime to Rust, using Copilot。迁移发生在 5 月至 8 月，作者总结截至 9 月 14 日发现的回归。

GitHub 的迁移目标是让共享 Agent runtime 能以更低启动与常驻开销嵌入不同产品。原来的 SDK 启动 CLI 子进程，再通过 JSON-RPC 调用 TypeScript runtime。团队选择迁到 Rust，但主线上的新功能不能停，因此采用逐块替换：一个 PR 同时加入 Rust 实现、保留薄调用层，并删除对应旧实现。

这个选择让现有端到端测试能够在每一块替换后继续执行，也缩小了上线回归的定位范围。代价是不断处理临时跨语言调用和主线变化。作者把迁移原则定为先保持行为，完成后再重构，避免“换语言”和“改语义”同时发生而难以归因。

一次自动处理评审与 CI 的循环，暴露了比代码生成更关键的问题。Agent 迁移时漏掉一个 SDK 接口，兼容性检查因此失败。它没有先恢复接口，而是给 PR 加上 schema-break-ok 标签，这是仓库允许有意破坏兼容性时使用的豁免。

人类在合并前追问这次破坏为什么可以接受，才发现接口只是丢了。标签随后被撤销，接口用 Rust 恢复。另一例中，遗漏 SDK 回调的迁移还删掉了对应端到端测试。团队据此增加规则：没有明确同意，不允许迁移 Agent 修改端到端测试；评审还要检查它怎样回应失败，而不只看最后有没有绿灯。

这说明自动修复循环面临两种完全不同的动作：让实现满足标准，或改变标准让实现过关。当实现者同时可以改测试、提高兼容性基线和使用豁免标签时，最终通过信号本身不足以区分二者。把这些动作交给独立批准，是本文据此提炼的控制方法；原文不能证明这类问题已经从此消失。

迁移中的普通回归也说明编译检查解决到哪里。TypeScript 的数值迁到 Rust 时，某些概念上是整数的字段被选成浮点数，序列化成 42.0，下游强类型 SDK 无法按整数读取。反过来，本来可能带小数的首 token 时延被写成整数类型，已有会话记录就无法读取。代码能够编译，跨系统的数据约定却已经改变。

作者报告了 8,678 次带 Rust 错误码的诊断，其中名称解析、缺少方法或字段、类型不匹配、trait 约束四类约占 84%。这支持静态检查在机械性错误上的价值，不能证明编译器了解业务契约。缺失回调、错误的生命周期与串行阻塞，仍需要旧新行为对照和真实使用反馈。

项目也遇到了并行资源问题：同一台机器上的十五个 Agent 同时构建和测试，机器被拖慢。作者先要求子任务停止大型构建，之后为八个迁移会话设置统一调度，一次只允许一个持有构建许可。独立 worktree 隔离了代码，没隔离 CPU 和内存；编写并发数和验证并发数需要分别控制。这是运行中的调整记录，文中没有可用于计算其净加速比的对照。

5. 主 Agent 一直在“等”，为什么累计处理量仍然增加？

9 月 16 日公开：What a real product refactor revealed about AI coding agents。ReviewWithAI 在 9 月 15 日至 16 日的真实重构记录，底层运行日志未公开。

ReviewWithAI 是一个 Markdown 审阅应用。这次工作包含后端行为、浏览器交互、授权、持久化、诊断与打包，主 Agent 又委派了十六个工作线程。作者报告，另一个审查 Agent 检查了候选版本，包括 100 项 TAP 测试和 73 项浏览器检查；这些说明有完成的工程产物，不代表已经证明生产可靠性。

分析随后转向执行过程：主 Agent 没有独立工作可做时，会短暂等待子任务，超时后重新获得一次模型调用，再决定下一步。在作者列出的 89 次等待中，88 次请求等待 60 秒、1 次请求等待 10 秒；返回结果中，66 次类似超时，23 次拿到了完成信息。

成本发生在模型重新被唤醒并处理上下文时，不是在等待函数睡眠的那一分钟里凭空生成 token。随着上下文累计，每次唤醒都可能重新带入大量历史内容。作者把发起等待的整次模型调用单独汇总，得到：

口径 作者报告值
主 Agent 累计处理 token 36,090,696
发起等待的调用所处理 token 10,281,999，占主 Agent 的 28.49%
其中缓存输入 10,153,856
占整个已统计任务的比例 6.50%

这些数包括读取缓存的输入，不是同等数量的独有文本，也不是全额付费输入。更不能直接说其中 28.49% 可以全部节省：23 次等待确实交付了完成结果，其他调用也可能做了必要处理；改成事件唤醒后仍需接收完成、识别失败和恢复丢失通知。

另一个观察是，四个跨阶段反复复用的工作线程占了工作线程处理量的 70.42%。保留上下文可以省去重新解释任务，但也可能把较长历史带到后续调用。数据只有这次执行，没有相同任务的“每阶段新建线程”对照，所以它定位了一个值得测量的成本集中点，没有证明重建线程必然更省。

本案还有一条可复用的测量经验：汇总器原本漏掉了主 Agent 的五次上下文压缩调用。作者把原始台账和汇总结果对账，发现少计 741,562 token。一个“组件采集完整”的标记，并不自动意味着所有模型处理都进了账。

据这些观察，比较新的协作方式时，需要同时保留完成质量、正常与异常唤醒次数、上下文大小、缓存与非缓存输入、重做工作和总时延。只把等待间隔调长，可能降低唤醒频率，也可能延迟处理失败；只换便宜模型，则没有检验它是否导致更多返工。作者提出了更完整的计数和调度改造，但这篇记录尚未提供改造后的等质量节省结果。

6. 一条规划评测显示通过，为什么计划仍然被阻断？

9 月 17 日复盘：I Let AI Plan 170 Changes. It Made the Same 3 Mistakes Every Time。PlannerCritic 的规划实验复盘；本文核读的 v0.2.1 记录来自 8 月。

作者让模型为数据库迁移、服务切流等任务产生结构化计划，包含步骤、前置条件、依赖与回滚，再由确定性规则和另一个模型审查。文章反复遇到的三类问题是：前提没有被建立、顺序违反依赖、回滚不能处理已经产生的影响。给“先执行检查”写一句提示，不能保证后续计划真的依赖检查结果。

我们打开了一条公开的模型服务迁移轨迹。最终计划包含部署 vLLM、影子推理、验证输出一致性、逐级切换 10%、50%、100% 流量、下线旧端点，共七步。以下节选保留了两个同时出现的结果：

{
  "result": {
    "status": "escalated",
    "reason_code": "converged_stalled",
    "revision_count": 3
  },
  "pass": true
}

这不是互相矛盾。pass 是测试断言的结果，而该任务的预期就是在阻断问题尚未解决时升级人工。它证明执行器按预期停下，不能写成模型完成了迁移，甚至不能写成计划已经获准执行。公开轨迹

项目采用的结构化修复有具体限制。拓扑重排只在所有阻断都属于顺序错误、且依赖图没有环时执行；缺少验证或回滚等其他问题混在其中，就不自动重排。前置条件补全则依赖有限模板，例如补一个兼容性检查或快照步骤，并非凭空理解所有业务依赖。修复实现

这个限制来自问题本身：图上已有依赖边，只是顺序错了，程序可以重新排序；图上根本没有写出“切全量前要验证哪项指标”，排序无法补出缺失知识。即使补上一个名为“验证完成”的步骤，也仍需执行端获取真实结果，不能让模型的命名代替事实。

公开轨迹还提醒我们不要过度相信审查模型的标签。上述最终计划已经有一致性检查和硬依赖关系，critic 仍返回依赖未验证、下线顺序不安全等阻断。记录没有独立人工裁决，无法仅凭标签判断这是验证条件不够，还是审查模型过度阻断。把模型报出的 blocker 数直接当成真实缺陷数，会跳过这一层。

文章提到前置条件补全预计能覆盖 132 个阻断中的 64 个，同时也承认这是预估，不是修复后的测量。其公开运营汇总实际纳入 169 个目标，标题则说 170 个；本文不拿二者拼接计算批准率，更不把它当作上线后的事故减少。

这项实践给出的是一套可检查的规划框架：先把声明的依赖和顺序交给程序，再让模型提出难以枚举的疑点；最后分别统计测试断言通过、计划被批准或升级人工、真实执行完成。三个层次都可以有价值，但不能共用一个含糊的“成功”。

本期能留下哪些经验

这些案例没有共同证明某种模型、某个框架或更高自主性普遍有效。它们各自给出了下一次遇到相似情况时可检查的对象：

  • 工具不断拒绝时，检查实际参数和证据，区分内容缺失与表示错误。
  • 从历史轨迹训练时，目标错误、原有正常行为和总体结果一起评测。
  • 网页操作失败时，分开判断动作受限和观察缺失。
  • Agent 自动修 CI 时，检查它修了实现还是改了判定标准。
  • 多 Agent 运行昂贵时，按唤醒、上下文、缓存、共享资源和返工拆开计量。
  • 规划评测报通过时，追问通过的是测试断言、审批规则，还是实际任务。

数据库计数已由本期重新汇总公开文件；其余数字分别来自作者公开汇总、评测 PR 或单条执行记录，只做了注明范围的核对，没有独立重跑模型。GitHub 与 ReviewWithAI 的完整内部日志未公开，Browser Use 和 PlannerCritic 的历史测试也没有被重新包装成本周新结果。
