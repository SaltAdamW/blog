Agent 历史经验选读五个具体问题

客服、编码与研究 Agent 的五条历史经验：出了什么问题，如何排查或调整，哪些条件不能照搬。

Adam
2026 年 9 月 22 日1,661 字 · 3 项一手资料本篇浏览 加载中
下载原稿

从客服、编码和资料研究三类场景出发，本文选取三篇一手复盘中的五个具体问题，讨论哪些排查线索和决策可以借鉴，以及它们成立的条件。这些记录不是五次独立实验。原文均已核读；经历和做法来自作者自述，尚未由我们独立复现。各节末尾的借鉴是基于这些记录的分析，不是已经验证的通用规则。

客户同时查物流和取消订阅，为什么整单转了人工？

原文：Robin Monnier，Field notes from running customer support AI in production，第 3 节。页面日期：2026-06-29，历史经验。

客户在同一条消息里说订单没有送达，同时要求取消订阅。作者的客服 Agent 只被路由进物流工作流，处理了配送问题，却发现当前工作流没有取消订阅的工具，于是把整个工单交给人工。局部任务已经处理，并没有避免整体转交。

作者没有选择开放全部工具：取消订阅还受确认步骤、挽留方案和权益规则约束，单独获得取消能力并不等于完成这套业务流程。他把问题定位为单意图路由，并提出分别执行两套携带各自规则的工作流。原文没有报告改后的转人工率，不能把这个方向写成已经验证的收益。

这条经验适用于“不同意图对应不同工具和规则”的系统。遇到类似失败，先查原始请求是否被完整拆分，再查工具是否缺失；不要直接用增加权限处理路由遗漏。若系统本来就支持多意图，还需继续检查工作流间的状态交接，不能照搬作者的诊断。

来源：https://robinmonnier.com/field-notes-from-running-customer-support-ai-in-production

一次物流接口异常，为什么后续对话也全部失败？

原文：Robin Monnier，同上，第 4 节。页面日期：2026-06-29，历史经验。

作者记录了一次承运商查询工具异常。异常不只影响当次查询：客户随后发送的每条消息也都报错。

按作者的排查，框架在模型决定调用工具时就保存了会话快照，工具却在结果写入前失败。持久化历史里留下了没有对应结果的工具调用；后续请求持续继承这个不完整历史，被模型 API 拒绝。原文解释了故障如何持续，但没有给出完整的状态修复实现和修复后的统计。

对有持久化会话的 Agent，可借鉴的排查顺序是：工具报错之后，不只检查外部服务是否恢复，还要检查保存的调用和结果是否配对。补写失败结果、回滚未完成轮次或其他恢复方式，需要结合实际协议验证；这些是我们可测试的方案，不是作者已经完成并证明有效的修复。

来源：https://robinmonnier.com/field-notes-from-running-customer-support-ai-in-production

Agent 改完代码后，应该不断修 CI 直到通过吗？

原文：Alistair Gray，Minions: Stripe's one-shot, end-to-end coding agents - Part 2，“… and iterate”。发布日期：2026-02-19，历史经验。

Stripe 的无人值守编码流程先在本地确定性执行一组 lint，再推送到 CI。遇到可自动修复的问题先应用修复；剩余失败返回给 Agent，再给一次本地修改机会。第二次推送和 CI 后，分支交回人工检查，不让 Agent 无限重试。

作者把这个上限解释为时间、计算和 token 成本的取舍，认为持续重复完整 CI 会遇到边际收益下降。这是他们采用的工程策略，文章没有提供不同重试上限的对照数据，不能说“两轮最优”。

可借鉴的是区分便宜且确定的局部检查与昂贵的完整反馈，再决定何时停止自动修复。若我们的任务没有人工接手，或单轮 CI 很短，就需要另行检验停止条件；照搬次数会丢掉这个策略成立的前提。

来源：https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2.md

仓库规范很多时，是否都应该放进全局提示？

原文：Alistair Gray，同上，“Context gathering: Rule files”。发布日期：2026-02-19，历史经验。

Stripe 报告，他们谨慎使用无条件全局规则，主要把规则限定到子目录或文件模式，让 Agent 访问相关文件时再加载。作者给出的理由是仓库规模太大，全部规则前置会挤占任务上下文。

这里可确认的是已经采用的规则组织方式和作者的设计理由，而不是一次有日志的上下文溢出事故。文章也没有量化按需加载对任务正确率的影响，不能把它写成已证明的准确率提升。

可借鉴的是先检查规则的适用范围，再决定加载位置。只影响某个模块的约定适合就近放置；必须始终遵守的约束不能仅因省上下文而移走。这个区分需要结合自己的仓库验证。

来源：https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2.md

三个研究 Agent，为什么两个在重复搜索？

原文：Anthropic，How we built our multi-agent research system，“Teach the orchestrator how to delegate”。发布日期：2025-06-13，历史经验。

团队早期允许主管只给子 Agent 一句简短任务，例如研究半导体短缺。实际运行里，一个子 Agent 研究了 2021 年的汽车芯片危机，另两个却都研究 2025 年的供应链。多个执行者没有自然形成互补分工：时间范围不一致，同时出现重复搜索。

作者因此强调，委派需要说明目标、输出格式、工具与信源建议，以及明确的任务边界。原文有这个失败案例，但没有单独给出这项修改减少重复搜索的幅度，不能把整套多 Agent 系统的收益归给任务描述。

对可并行的资料研究，可借鉴的是在派工前明确时间范围和子问题边界，而不是只增加执行者。若任务本身高度依赖前一步结果，拆得再详细也未必适合并行；此时应先检验任务之间能否独立推进。

来源：https://www.anthropic.com/engineering/multi-agent-research-system

从这些记录中学什么

这些经验分别提供一种排查线索或决策参照，而不是替所有 Agent 规定统一做法。真正需要保留的是“在什么条件下出现了什么反馈，所以检查或调整了哪一步”。相似任务可以据此减少盲试；条件不同、效果未报告或只有作者解释的地方，仍需自己的验证。
