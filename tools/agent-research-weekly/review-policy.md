# 周报与技术长文的追问审稿约定

确认日期：2026-09-22。依据：用户认可本轮周报的追问方式，并要求后续默认采用。
范围：周报与技术长文的内容 review、重要返修和发布前内容审查；不扩展为普通代码 review。

## 目的

读者需要从实际案例学会判断：什么条件下遇到问题，哪个动作改变了结果，证据支持到哪里，遇到相似情况能借鉴什么。
只列事故、数字或“加强验证”等建议不够。追问用于找到解释断点，并形成有来源、能落实的修改稿，而不是增加术语、篇幅或统一套用模板。

## 默认流程

1. 读取待审稿、已有原文与来源清单，固定版本或正文哈希；读取已安装的 `strict-interviewer` skill，继续遵循其过程记录与深化要求。
2. 沿用双角色材料问答：追问者负责提出问题，回答者依据正文和材料作答，主会话逐次转发、核对和记录。此用途已有用户的持续授权；不需要每次再问是否启动双角色。
3. 一次一个核心问题，依据上一轮回答跟进。完整稿默认覆盖下面五层，每层一个主问与一个跟进，约十轮；重要缺口可在 skill 上限内继续追问。局部返修只复查受影响层，注明本次范围，不虚称重新完成全部问答。
4. 将全部高、中优先级问题逐项深化：问题定义、两至三个候选方案及取舍、推荐理由、最小验证、具体表达或局部替换稿、下一步和证据缺口。不能问答结束后只交付问题清单。
5. 按 skill 保存问答记录、深化册和核心摘要。记录实际问答，摘要不冒充逐字实录；文件使用中性名称，保存于调用时目录或用户指定位置，不混入公开正文。
6. 有正文修改授权时落实局部返修，复查新增事实和受影响推导；仅要求 review 时先交付建议。改变主问题、核心结论或章节关系仍需框架确认。发布遵循既有授权，不以 review 通过替代发布许可。

## 五层问题

| 层次 | 需要追到的具体内容 |
| --- | --- |
| 问题与目标 | 谁在什么场景失败；原方法在哪一步失效；想改变的动作和最终任务结果是否混淆 |
| 替代方案 | 局部补信息、改接口或简单工具是否已够用；所选方法为什么值得承担新增成本；哪些比较只是编者分析 |
| 机制与代价 | 具体输入、判断、执行和反馈如何变化；历史经验怎样写入、读取、生效、更新或撤销；失败边界在哪里 |
| 数据与验证 | 基线、版本、样本、分子分母和判分口径；代理指标与任务质量、token 与费用、单步与全流程的区别；负结果和漏项 |
| 迁移与迭代 | 哪些条件相同才可借鉴；条件变化后哪里失效；下一次应检查或尝试什么；计划、建议和已执行结果分别是什么 |

五层用于审稿，不要求将每节正文改成五段或五张表。自然、准确的段落可以保留。

## 证据与收尾

- 使用已有材料能解决的问题先核读；需要新资料时按研究技能定向补证。原文没读到与作者没披露分开处理，不为完整故事补造尝试、因果或数据。
- 周报继续核对发布日期、实验发生日期和当期窗口，不把旧实验或本次重读包装成本周新结果。
- 保留作者实测、公开轨迹、本轮算术核对、独立复现和编者建议的区别。没有新实验就不声称验证了业务收益。
- 用精确表述、具体机制和真实反例改善正文，不在强结论后堆免责声明，不把全部案例改成审计清单。
- 完成前回读三份记录，确保高、中问题都有处理方案，新增事实可追溯，未解决问题明确。轮数、字数、自评分不能替代这些检查。
- 影响主结论的证据缺口未解决时，补证或收窄结论；不能仅因问答结束就宣布成稿可发布。

## 自动宿主的执行边界

定时周报由 Python 宿主编排追问者和回答者的独立受限调用。每个问题单独生成，再将它连同此前实际问答交给回答者；下一问携带此前回答。模型没有 shell、MCP 或子进程启动权，宿主按固定流程调用，不能靠一次响应生成整份对话。

`deliver`、`retry` 和手动 `publish` 在新推送前都必须完成十轮问答、全部高中问题深化、最多一次局部返修，以及独立的事实复核和解释复查。仅 `run` 生成的本地草稿不视为已完成追问；`review` 可单独执行本流程，不发布。

原稿、每步请求与响应、三份研讨文档和最终结果分别绑定哈希。模型调用失败可从已完成步骤继续；若复核明确不通过，重试复用该结论，不反复抽样直到通过。补证或修改原稿后形成新的审稿版本。材料超出预算时停止，不静默截断。

已推到远端的旧版本提交可以继续做上线回读，不重新写稿或推送；没有追问记录的旧版本待推送提交必须停止。独立长文宿主仍按现有框架与成稿确认执行，本版未将该编排接入其自动调用；交互式长文审稿继续遵循上述默认约定。
